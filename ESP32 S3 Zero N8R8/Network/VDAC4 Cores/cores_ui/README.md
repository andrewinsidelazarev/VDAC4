# VDAC4 Cores UI — этап 3, карточки в ELF ядер

Этап 3 выполнен. Утверждённый дизайн сохранён. Тексты, рисунки, категория,
акцент и Manage для NES/NEXT/AMIGA находятся в их `.vdac4.card`; рендер получает
указатель из модели. Встроенная таблица знакомых систем удалена. Без карточки
показывается общий вид «FPGA core». Экран предназначен для будущего отдельного
`COREMENU.ELF`; его сборка и встраивание выполняются отдельно.

Открыть **[галерею](previews/index.html)**, [список кадров](STAGE1.md),
[главный экран](previews/01_menu_nes.png) или [анимацию](previews/motion_25fps.apng).
Формат и создание карточки нового ядра в три шага — **[CARD.md](CARD.md)**.

## Повторить всё одной командой

Из `cores_ui`:

```powershell
.\test_stage3.cmd
```

Команда строит card.bin, копии настоящих ELF, проверяет вставку/замену раздела,
штатные валидаторы, парсер и рендер на ПК и под ASan, компилирует четыре объекта
Xtensa GCC 15.2, считает размеры, обновляет PNG/APNG и сверяет пиксели с эталоном.
Вывод, временные файлы и сборки — **`build-pc` на E:**. Сводный результат —
[stage3_result.json](build-pc/stage3_result.json), хеши исходников —
[stage3_inputs.json](build-pc/stage3_inputs.json). Исходные ELF только читаются.
Прошивка, плагин, сборки ядер, сеть и плата не изменяются.

Используются уже установленные Python/Pillow из `E:\zx\esp\pio-venv`, LLVM
из `E:\zx\llvm`, Xtensa из пакета `esp-15.2.0_20251204`. Установок нет.
TEMP/TMP и Python направлены так, чтобы временные файлы оставались на E:.
Отдельные части: `test_stage3.cmd --only fixtures|loader|parser|host|asan|xtensa|previews`
(указать одно значение; после чистой папки сначала fixtures). `test_stage2.cmd`
остаётся совместимой командой полного запуска. Для одних картинок —
`cui_preview.cmd`, для упаковки уже созданных RGB565 — `cui_preview.cmd --no-build`.

## Дизайн

Идея — небольшой каталог настоящих машин. Слева карточки с миниатюрами корпусов,
справа большая иллюстрация и сведения о выбранной системе. Прямоугольные панели,
приглушённые дорожки платы, светлый текст, мягкий цветовой акцент.
Силуэты нарисованы заново геометрическими примитивами. Логотипов производителей,
заимствованных тем, экранов других оболочек и загруженных изображений нет.

Основной пример сохраняет порядок карты **NES → NEXT → AMIGA**, 886 KB и собственный
слой ESP у всех трёх. Сортировки нет. До трёх ядер показаны крупные карточки,
для длинного списка — пять строк около выбранной, полоса положения и номер `09 / 12`.
Одно ядро не дублируется для заполнения пустого места.

Ядро без карточки получает заголовок `FPGA core`, полное имя `ИМЯ.BIN` и рисунок
платы. Длинная строка списка сокращается целым символом с многоточием. При общем
слое ESP явно указано, что клавиатура недоступна. Встроенного каталога систем нет. C64/MSX/SMS/PCE без карточек, как и любое
другое имя без карточки, используют общую иллюстрацию платы.

выходить за безопасную зону. Превью — **RGB565 640×360 → nearest-neighbour ×2 →

(`r5<<3 | r5>>2`, `g6<<2 | g6>>4`), как на выходе Tang.

## Движение и передача

Вызовы `cui_render` — каждые **40 мс**, 25 раз/с. При смене выбора содержание карточки
обновляется один раз; маркер списка проходит к новой строке за **240 мс** по
целочисленной кривой `3t²−2t³`. На тот же срок световая дорожка вырастает до полной
ширины. Маленькая точка на её конце плавно меняет яркость с периодом 2 секунды.
Большой корпус, фон и текст не перемещаются и не мигают между шагами.

Если процентов нет, индикатор состоит из трёх точек с шагом 160 мс и циклом 960 мс.
У него нет шкалы, выдуманных процентов или обратного отсчёта. В `COPYING_CACHE`
процент 0…100 показывается только когда его передала обвязка. 45 % в превью —
демонстрационный вход. Ошибки неподвижны. Финального «успеха» нет: FPGA может
перехватить экран на любом кадре.

APNG содержит ровно **100 кадров по 40 мс**, в том числе повторяющиеся кадры:
NES → NEXT → AMIGA → NEXT → NES → запуск ESP → кэш без процентов → ПЛИС.
Это четыре секунды, зацикленные для просмотра. Задержки CPU/LINK в APNG не
моделируются; это визуальная временная шкала, не запись устройства.

Fade выполняет обвязка общей прозрачностью за ~0,3 с. PNG 23–25 используют
`background + floor((overlay-background)*(alpha+1)/16)` для alpha 4/8/12.
Ноль всё ещё даёт 1/16 оверлея; полное исчезновение требует выключить оверлей.
Фон взят из разрешённого `Sound/player_ui/previews/29_wc_background.png`:
это **макет WC с окном плеера**, не реальный снимок плагина и не часть прошивки.

## Клавиши

| Состояние | Действие |
|---|---|
| Меню | ↑/↓ — предыдущая/следующая запись; Enter — запуск; Esc — назад |
| Подключение / чтение списка | Esc — назад, показано как предложение для обвязки |
| Запуск ESP / загрузка | F12 — возврат в Wild Commander |
| Ошибка | Esc — возврат в Wild Commander |

Новые ←/→ или PgUp/PgDn не нужны. UI не обрабатывает клавиши, не меняет выбор и не
решает, можно ли запускать ядро: он отображает готовую модель плагина.

## Интерфейс с обвязкой

```c
int cui_init(cui_canvas_t* canvas,
             void* (*alloc)(size_t size, int psram, void* ctx), void* ctx);
int cui_render(const cui_model_t* model, uint32_t now_ms, int full,
               cui_canvas_t* canvas, cui_rect_t* dirty, int max_dirty);
void cui_reset(void);
```

`init` возвращает 1 при успехе, 0 при ошибке. Холст принадлежит вызывающему,
размер ровно 640×360, stride измеряется в точках и может быть больше 640.
Единственный запрос памяти — 460800 байт, `psram=1`. Кэш содержит статический
кадр без движущихся элементов; кадры не выделяют память. Повторный `init`
переиспользует кэш и сбрасывает историю. Один экземпляр, последовательные вызовы.

Владелец сохраняет указатель, возвращённый своим alloc. После `cui_reset()`
он может освободить его собственным механизмом. `reset` сам ничего не освобождает,
потому что заданный callback-интерфейс не содержит release. Не освобождать память,
пока UI её использует. Новый `init` после `reset` снова вызывает alloc.

Модель описана в [cores_ui.h](cores_ui.h). Имена — до 15 символов без расширения,
размер — байты, `own_esp_layer` — булев флаг. До 32 записей, порядок входа сохранён.
`selected` — индекс с нуля. `count=0` в меню отображается как отсутствие ядер.
Число записей ограничивается 32, выбор — существующим диапазоном.

Поле записи **`const cui_card_t *card`** указывает на проверенную карточку в arena
владельца; NULL даёт общий рисунок и тексты. Поле manage_key из модели удалено.
Клавиша берётся только из карточки: NES — F1, NEXT — F1, AMIGA — F11. Если
карточки или клавиши нет, строка скрыта даже при знакомом имени ядра. У общего
слоя всегда `Shared ESP layer`. Manage сообщает клавишу меню **запущенного ядра**.
Размер структуры изменился; будущую обвязку нужно собирать с актуальным заголовком.
Точные объявления парсера, arena и callback — в [CARD.md](CARD.md#интерфейс-c).

`revision` увеличивают при изменении **статических данных**: имён, размеров,
флагов, указателей/содержимого карточек, текста ошибки. Выбор, count, state и error дополнительно сравниваются
самостоятельно. Изменение `progress_percent` не требует revision: оно обновляет
только индикатор. Не увеличивать revision просто по таймеру или при каждом проценте,
иначе получится полная перерисовка. `now_ms` — монотонный uint32_t, в миллисекундах.

Дополнительные поля к примерной модели задания — явное перечисление ошибок,
`progress_percent=-1` для неизвестного значения и `error_text[61]` для сообщения ESP.
Версии не выведены, поскольку они необязательны и реальных значений для примера нет.
Вместо сетевых операций и таймеров плагина UI получает одно из восьми состояний.

`full` восстанавливает весь кадр из кэша и рисует динамику на текущее время.
При новой модели сначала пересобирается кэш. Прямоугольники полуоткрытые,
оба x чётные. Рекомендуется **8 слотов dirty**, для текущей динамики достаточно 2.
При нехватке слотов области объединяются в последнем: точки не теряются,
но передаваемая площадь возрастает, особенно при `max_dirty=1`.
Нулевые указатели, неверный холст, `max_dirty<=0` или отсутствие init дают 0 без рисования.
После отправки возвращённых областей обвязка оставляет содержимое холста неизменным
до следующего render. При внешней порче холста нужен `full=1`.

В коде отрисовки нет ОС, ESP-IDF, double, исключений, RTTI, STL и malloc/new.
Используются стандартные `memcpy`, `snprintf`. Результат анимации зависит
от модели, времени и истории выбора после init; одинаковая последовательность входов
воспроизводит те же пиксели на проверенных последовательностях этапа 2.
Повтор одного времени не двигает анимацию; вне обычного расписания 40 мс
отрисовка также учитывает каждый новый `now_ms`, включая переполнение uint32_t.

## Проверки этапов 2 и 3

Обычная сборка ПК и ASan дали одинаковый успешный результат:

- Парсер: **864637 проверок**, 85 отрисовок общего вида после отказа,
  **6000** мутаций с фиксированным seed; все усечения NES card.bin и ELF.
  Проверены повреждённые/чужие таблицы, переполнения смещений, отсутствие/дубликат
  секции, ALLOC и неверный тип, CRC, строки/NUL/ASCII, гигантские размеры,
  RLE с нулевыми сериями, плохими индексами, недобором и перебором точек.
- Callback: максимальный запрос **512 байт**, без пересечения сектора;
  отказ на каждой из **57** операций чтения корректной NES-карточки возвращает NULL.
  Проверены выравнивание/границы arena, недостаточный буфер, NULL и время жизни копий.
- Инструменты: детерминизм, ограничения JSON/PNG/цветов/alpha, ошибка CRC,
  вставка и замена карточки. Значения Manage F1/F1/F11 подтверждены из ELF.
- Все шесть ELF после вставки/замены прошли **настоящий** `elfImageProblem()`
  из Firmware и оригинальный `Sound/tools/check_module_symbols.py`.
  Загружаемые секции, индексы, релокации, символы, entry и program headers
  совпадают с оригиналами; хеши оригинальных файлов не изменились.
- Рендер: **3148 кадров**, **29480157** изменившихся точек, **1081** полный кадр,
  **128** пустых обновлений; 13 независимых пиксельных проверок строки Manage.
  Все 0…32 ядра, длинные/неизвестные имена, обе стороны прокрутки, 64 пары состояний,
  меню → загрузка → ошибка, проценты 0…100 и обратно, границы холста, чётные x,
  stride 640/648, нерегулярные timestamps, переполнение времени, отказы init.

Стенд рендера сравнивает три независимых экземпляра: частичный, полный и повтор
той же последовательности. Каждая изменившаяся точка обязана лежать в объединении
dirty; отдельный «Tang» получает только эти области и тоже совпадает с полным
холстом. Под ASan ошибок памяти не обнаружено. Максимальная обычная частичная
площадь при двух и более слотах — **5400 точек**; при одном объединённом слоте —
**127872**. Рекомендуются восемь слотов, минимум два для обычного бюджета передачи.

Исправления этапа 2 сохранены: отдельные строки для последовательных if,
прокрутка только при count>5, обновление анимации при каждом новом now_ms.
Тесты Manage адаптированы к новой модели: ключ только в карточке, пустой ключ,
отсутствие карточки даже у NES, восемь знаков, Shared с любым ключом, карточка
при изменённом имени BIN. Максимальные строки карточки проверены отдельно.

Логи: `build-pc/card_host.log`, `card_asan.log`, `stage2_host.log`,
`stage2_asan.log`, `loader_check.log`, `module_symbols.log`, `card_*`, `add_*`,
`replace_*`. Проверки не исполняют код ядер и не моделируют время платы.

## Размеры Xtensa GCC 15.2 и память

Компилятор **xtensa-esp32s3-elf-g++ 15.2.0**, пакет `esp-15.2.0_20251204`.
Все рабочие исходники чисто проходят
`-std=c++17 -O2 -Wall -Wextra -Werror -fno-exceptions -fno-rtti`, дополнительно
`-mlongcalls -ffunction-sections -fdata-sections -fstack-usage`.

| Объект | text (код + const), байт | data | bss |
|---|---:|---:|---:|
| `cores_ui_xtensa.o` | 9874 | 0 | 72 |
| `cui_card_xtensa.o` | 2830 | 0 | 0 |
| `pui_font_xtensa.o` | 83958 | 0 | 0 |
| `cui_art_xtensa.o` | 7572 | 0 | 0 |
| **Сумма** | **104234** | **0** | **72** |

Инструкции `.text` — **9901**, литералы — **860**, `.rodata` — **93473** байта.
Сумма text уменьшилась относительно этапа 2 на **8663 байта**, несмотря на
добавление парсера. Это размеры объектов до финальной линковки, без кода
стандартной библиотеки и служебных ELF-секций. `COREMENU.ELF` не собирался.
Таблицы машин в эти объекты не входят: их RLE находятся в карточках ядер.

| Ресурс | Размер |
|---|---:|
| Холст вызывающего | 460800 байт |
| Кэш рендера, один alloc с psram=1 | 460800 байт |
| Консервативная arena одной карточки | 25600 байт |
| card.bin NES / NEXT / AMIGA | 2134 / 4454 / 4852 байта |
| Общая плата, палитра и дескрипторы Xtensa | 2660 байт |
| Таблицы фона | 4912 байт |

Точный объём arena зависит от ABI и размера blob:
`sizeof(cui_card_t) + alignof(cui_card_t) - 1 + card_bytes`.
Его возвращает `cui_card_arena_required`. На x64 размер структуры 848 байт,
на Xtensa — 836 (проверено отдельным объектом ABI); для трёх готовых карточек достаточно соответственно
2989/5309/5707 или 2973/5293/5691 байт с запасом выравнивания.
Кэш + три точные arena на Xtensa — **474757 байт**, ниже 512 КиБ, без холста.
Для 32 карточек предельного размера нужна отдельная политика хранения:
32 консервативных arena займут 819200 байт, помимо кэша. UI сам их не выделяет.

Парсер не имеет bss и heap-зависимостей. Внешние функции обоих модулей —
`memcmp`, `memcpy`, `memmove`, `snprintf` и свои const-таблицы. Placement new
в парсере не выделяет память. Объектные зависимости malloc/new, исключений и RTTI
отсутствуют. Размеры отдельных кадров стека из `.su` не включают полный стек
вызывающего и callback, поэтому не являются лимитом стека задачи.
Исходные размеры/команды: `xtensa_sizes.json`, `xtensa_size.log`,
`xtensa_sections.log`, `xtensa_undefined.log`, `*_xtensa.su`, `build_xtensa_*.log`.

## Бюджет передачи и оставшиеся измерения

По заданной скорости 0,4…0,5 мкс за слово из двух точек обычные 5400 точек
требуют **1,08…1,35 мс LINK**. Полный кадр — **46,08…57,60 мс LINK** плюс CPU,
возвращается при открытии, смене карточки/состояния и статических данных.
Обвязка должна продолжать анимацию по текущему now_ms после полной передачи,
без накопления просроченных кадров. В Tang нет двойного буфера; поведение
смены карточки нужно оценить на ТВ при последующем встраивании.

Замеры ПК лежат в `build-pc/benchmark.json`, `preview_metrics.csv` и
`previews/render_stats.json`; они не подтверждают CPU ESP. Цели 6 мс обычный /
60 мс полный на ESP и реальная передача LINK остаются аппаратными измерениями.
Чтение карточек, выделение arena/PSRAM, fade, клавиши и реальные проценты
обеспечит владелец отдельного COREMENU.ELF. Встраивание в прошивку и плагин
в этот этап не входит.
