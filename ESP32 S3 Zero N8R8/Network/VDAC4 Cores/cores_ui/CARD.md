# Карточка ядра VDAC4, версия 1

Карточка находится в ELF самого ядра, в разделе **`.vdac4.card`**, тип
`SHT_PROGBITS=1`, `sh_flags=0` (в частности, **без SHF_ALLOC**), `sh_addr=0`,
`sh_addralign=1`. Рендер получает разобранную карточку из модели; имя BIN не
используется для поиска встроенных метаданных. Общая карточка остаётся в рендере.

`Firmware/src/elf_image.cpp` проверяет границы и имена **всех** разделов, а также
таблицы символов и релокации. Флаг ALLOC определяет набор загружаемых разделов.
Поэтому одного отсутствия ALLOC недостаточно: полученные ELF проверены настоящим
`elfImageProblem()` и оригинальным `Sound/tools/check_module_symbols.py`.

## Бинарный формат

Все числа little-endian. Заголовок — ровно 64 байта. Размер всей карточки,
включая заголовок, **64…24576 байт**; фактически допустимая карточка должна
содержать непустой title, палитру и оба изображения.

| Смещение | Размер | Значение |
|---:|---:|---|
| 0 | 8 | Байты `56 44 34 43 41 52 44 00`, то есть `VD4CARD\0` |
| 8 | 2 | Версия: 1 |
| 10 | 2 | Размер заголовка: 64 |
| 12 | 4 | Размер всей карточки; равен размеру раздела |
| 16 | 4 | CRC32 всей карточки с обнулёнными байтами 16…19 |
| 20 | 2 | Цвет акцента RGB565 |
| 22 | 2 | Число элементов общей палитры, 1…256 |
| 24 / 26 | 2 / 2 | Ширина / высота значка, 1…56 / 1…28 |
| 28 / 30 | 2 / 2 | Ширина / высота большой картинки, 1…256 / 1…128 |
| 32 / 36 | 4 / 4 | Длина RLE значка / большой картинки в байтах |
| 40…55 | 8 × 2 | Длины восьми строк в порядке таблицы ниже |
| 56 | 4 | Флаги, обязательно 0 |
| 60 | 4 | Резерв, обязательно 0 |

CRC — CRC-32/ISO-HDLC: отражённый полином `0xEDB88320`, начальное значение
`0xFFFFFFFF`, финальный XOR `0xFFFFFFFF`. Совпадает с `zlib.crc32()` при
обнулении поля CRC. Это проверка повреждения данных, не подпись происхождения.

Сразу после заголовка, **без выравнивания и разделителей**, следуют:

1. Восемь строк подряд в порядке ниже; в файле нет завершающих NUL.
2. `palette_count` цветов `uint16_t` RGB565.
3. RLE значка.
4. RLE большой картинки. После неё нет дополнительных байтов.

| Строка | Максимум байтов | Назначение |
|---|---:|---|
| `title` | 48 | Заголовок большой карточки; обязательна |
| `full_name` | 96 | Пояснение под заголовком |
| `year` | 8 | Год |
| `manufacturer` | 48 | Производитель |
| `line1` | 32 | Первая строка короткого описания |
| `line2` | 32 | Вторая строка описания |
| `category` | 16 | Категория в коротком списке |
| `manage_key` | 8 | Клавиша меню ядра, например `F1` или `Ctrl-F11` |

Каждый байт строки — печатный ASCII `0x20…0x7E`. NUL, управляющие символы и
UTF-8 не допускаются. Остальные строки, кроме title, могут быть пустыми.
Парсер добавляет завершающие NUL в разобранную структуру. Год и производитель
рендер объединяет через ` / `, если обе строки заполнены.

RLE — последовательность пар `(uint8_t count, uint8_t palette_index)`.
`count=1…255`; индекс строго меньше числа цветов. Пиксели идут слева направо,
сверху вниз; серия может пересекать границу строки. Сумма серий обязана быть
ровно `width*height`. Поток непустой, чётной длины, не длиннее `2*width*height`.
Индекс **0 означает пропуск пикселя**, независимо от RGB565 в palette[0].
Чёрный непрозрачный пиксель использует ненулевой индекс с цветом 0.

Размеры принятых рисунков — 56×28 и 256×128. Меньшие рисунки разрешены:
рисуются от той же верхней левой точки, без растяжения. Версия 1 не допускает
неизвестных полей в хвосте или ненулевого резерва; расширения требуют новой версии.

## Интерфейс C

Точные объявления из [cui_card.h](cui_card.h):

```c
typedef int (*cui_read_fn)(void *ctx, uint32_t offset, void *dst, uint32_t count);

size_t cui_card_arena_required(uint32_t card_bytes);
const cui_card_t *cui_card_parse(const void *data, uint32_t size,
                               void *arena, size_t arena_size);
const cui_card_t *cui_card_read_elf(cui_read_fn read, void *ctx, uint32_t file_size,
                                  void *arena, size_t arena_size);
```

`read` возвращает **0 только после успешного копирования всех count байтов**,
любое другое значение — отказ. Ни один запрос не превышает 512 байт и не
пересекает границу сектора 512. Смещение может быть невыровненным: адаптер читает
соответствующий сектор и копирует запрошенную часть. При неполном последнем
секторе нужно обеспечить только запрошенные байты. Пример такого адаптера для
ПК — [tests/card_fixtures.h](tests/card_fixtures.h).

`file_size` — достоверная длина открытого файла, переданная владельцем.
Чтение синхронное; файл должен оставаться неизменным до возврата. Парсер последовательно
читает ELF-заголовок, записи таблицы разделов, имена и выбранную карточку.
Весь ELF и вся таблица разделов в RAM не копируются. Последовательные запросы
могут повторно читать один сектор; адаптер может кешировать его.

Поддерживаются ELF32 LE, Xtensa `e_machine=94`, `ET_EXEC=2`/`ET_DYN=3`,
заголовок 52 байта, записи разделов 40 байт, 1…1024 раздела, таблица имён до
65536 байт, каждое имя до 255 байт плюс NUL. Расширенная нумерация ELF не
поддерживается. Если есть program headers: до 128 записей по 32 байта.
Карточка должна быть единственной секцией с точным именем `.vdac4.card`.
Проверяются границы, перекрытия служебных таблиц с секциями, все имена,
перекрытие карточки с другими секциями, тип/флаги, заголовок карточки,
строки, палитра, RLE и CRC. Арифметика границ не опирается на переполняющиеся суммы.
Разбор карточки не заменяет проверку исполняемого модуля загрузчиком:
символы, релокации и допустимость запуска проверяются отдельно.

Обе функции разбора возвращают **NULL при любом отказе**, включая отсутствие
карточки, ошибку чтения и недостаточную arena. Передача NULL в модель даёт общий
вид «FPGA core». Парсер не выделяет память; у него нет изменяемого глобального
состояния. Рабочие небольшие буферы находятся на стеке, результат — только в arena.

`cui_card_parse` копирует входные данные в arena. Входной blob после возврата
можно освободить. В arena находятся структура, копии строк, палитра в нативных
uint16_t и исходные сжатые потоки; картинки не распаковываются целиком.
Указатели `icon.rle`/`image.rle` указывают внутрь той же arena. Выделяющий `new`
не используется: placement new лишь начинает жизнь структуры в готовом буфере.

Arena может иметь произвольное выравнивание. `cui_card_arena_required(n)` даёт
гарантированный размер с запасом выравнивания или 0 при n вне 64…24576.
`CUI_CARD_ARENA_BYTES=25600` достаточно для любой допустимой карточки на
проверенных x64 и Xtensa; условие защищено static_assert. При отказе содержимое
arena может измениться. Переиспользование arena аннулирует предыдущий результат.
Вызывающий гарантирует доступность переданных буферов указанного размера.

Модель содержит `const cui_card_t *card`, отдельного manage_key в `cui_core_t` нет.
В рабочую модель передают только результат успешного разбора либо NULL, а не
непроверенную вручную собранную структуру. Пока модель использует карточку,
arena должна существовать и оставаться неизменной. При замене указателя/данных
увеличивают `model.revision`. Свой ESP и непустой ключ дают `Manage - <ключ>`;
без карточки или ключа строка скрыта. Общий слой всегда даёт `Shared ESP layer`.

## Карточка нового ядра: три шага

Все команды выполняются из `cores_ui`, Python — имеющийся
`E:\zx\esp\pio-venv\Scripts\python.exe`. В командах ниже `python` обозначает этот
интерпретатор; `-B` запрещает временные `__pycache__`. При сборках задавайте
`TEMP` и `TMP` на `cores_ui\build-pc` на E:; `test_stage3.cmd` делает это сам.

1. Создать `cards/NEWCORE/card.json`, `icon.png`, `image.png`, взяв NES за пример.
   PNG: максимум 56×28 и 256×128, alpha только 0/255, суммарно до 255 разных
   непрозрачных RGB565-цветов. Цвета квантуются отсечением младших битов, без
   dithering. `accent` — `"#RRGGBB"` либо целое RGB565 0…65535. Неизвестные поля
   JSON и выход за пределы отклоняются; рисунки автоматически не уменьшаются.
2. Собрать blob:
   `python -B tools/make_card.py cards/NEWCORE/card.json cards/NEWCORE/icon.png cards/NEWCORE/image.png cards/NEWCORE/card.bin`.
   Последний аргумент необязателен, по умолчанию `card.bin` рядом с JSON.
3. Вставить blob в **копию** ELF и проверить её:
   `python -B tools/add_card.py build-pc/NEWCORE_original.ELF cards/NEWCORE/card.bin build-pc/NEWCORE.ELF`.
   Затем `build-pc/loader_check.exe build-pc/NEWCORE.ELF` и
   `python -B ../../../Sound/tools/check_module_symbols.py build-pc/NEWCORE.ELF`.
   `loader_check.exe` собирается командой `test_stage3.cmd` из настоящего
   `Firmware/src/elf_image.cpp`. Для NES/NEXT/AMIGA все эти шаги автоматизированы.

`add_card.py` сохраняет индексы, адреса и байты старых секций, program headers,
символы и релокации. Новая карточка, таблица имён и таблица разделов дописываются
в конец; в ELF-заголовке меняются только e_shoff и при добавлении e_shnum.
Повторный запуск заменяет единственную активную карточку. Старые неиспользуемые
байты остаются в файле: для компактного результата начинайте с исходной копии ELF.
Без аргумента выхода заменяется входной файл. Оба инструмента разрешают запись
только внутри `cores_ui` или `E:\zx\cache\tmp\codex_cores_ui`.

## Готовые карточки и проверки

| Ядро | Manage | card.bin, байт | ELF исходный → с карточкой, байт |
|---|---|---:|---:|
| NES | F1 | 2134 | 43912 → 46716 |
| NEXT | F1 | 4454 | 21416 → 26540 |
| AMIGA | F11 | 4852 | 39752 → 45272 |

Исходные ELF только читаются. Рабочие копии лежат в `build-pc/elf`.
Исходники рисунков и тексты — `cards/<имя>/`; права на собственные рисунки
описаны в [assets/LICENSE.txt](assets/LICENSE.txt).

Полный запуск: **`.\test_stage3.cmd`**. Он проверяет инструменты, вставку/замену,
валидаторы ELF, callback 512, каждый усечённый префикс NES ELF/card, ошибки
структуры/CRC/RLE/строк/границ, 6000 воспроизводимых мутаций, каждый отказ чтения,
arena и безопасный общий вид. Повторяет проверки с ASan, тесты рендера этапа 2,
сборку Xtensa и сравнение дизайна. Итоги и ограничения измерений — в [README](README.md).
