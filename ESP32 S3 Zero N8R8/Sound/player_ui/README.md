## Дизайн

Тёмный сине-серый фон, мягкое неподвижное свечение возле обложки, мятный акцент,
тёплая обложка. Цвет не зависит от содержимого обложки — контраст текста остаётся
предсказуемым. В режиме без обложки — процедурный рисунок концентрических дорожек.
Ошибки выделены красной полосой и текстом, загрузка/ожидание/пауза — янтарным.

| Элемент | Цвет до RGB565 |
|---|---|
| Фон | `#0A1019`, плавное свечение до `#0F1F2A` |
| Основной текст | `#E9F1F3` |
| Вторичный текст | `#92A8B5` |
| Акцент | `#5CE2C6` |
| Предупреждение | `#FFC465` |
| Ошибка | `#FF7875` |

Градиенты фона, декоративной заглушки и столбиков квантуются с матрицей Bayer 4×4,
закреплённой в координатах холста. Нет шума, меняющегося между кадрами, фон не мигает.
Оверлей целиком непрозрачный; скругления нарисованы на его собственном фоне.

Шрифт **PUI Sans** нарисован для задания. Размеры генерации — 13, 16, 24 точки
холста; высота прописной буквы малого размера примерно 10 точек. Штрихи
сглаживаются на холсте, хранятся как покрытие 4 бита/точку. Три набора по 224 знака:
ASCII, кириллица и остальные печатные коды CP866; управляющие байты заменяются `?`.
Знак градуса — собственный, код CP866 `0xF8`.

Оригинальные контуры и таблицы лицензированы MIT, встраивание разрешено.
FreeSans и шрифты Windows в артефактах не использованы: у найденного FreeSans
в таблице имени указана GPL, но локального текста исключения для шрифта не найдено.

| Логотип и номер трека | y=20; разделитель y=47 |
| Обложка | x=32, y=64, **192×192** |

| Исполнитель | y=120, шрифт 16 |
| Альбом и год | y=146, шрифт 13 |
| Формат / подробности | y=176 / 196, шрифт 13 |
| Подписи анализатора | y=213 |
| Столбики | x=248…600, y=230…258, 352×28 |
| Транспорт и время | y=273…301 |
| Полоса прогресса | x=32…608, y=306…309 |
| Громкость, температура, клавиши | y=331 |

Всё значимое внутри безопасной зоны 16…624 × 9…351, с дополнительными полями.
Постоянная разметка сохраняется при загрузке, паузе, ошибке и отсутствии меток.
Список станций занимает правую часть, показывает пять строк вокруг текущей;
для длинных списков есть индикатор положения. Таймер показа списка на 10 секунд
остаётся обязанностью плагина/обвязки.

Длинные название, исполнитель, формат и другие строки обрезаются по целому
символу с `...`. Бегущей строки нет — это предусмотренный заданием вариант.
Файл без меток использует имя файла; радио без ICY — состояние или название станции.
Длительность 0 даёт `--:--`, радио — `Listening time`, часы выводятся как `h:mm:ss`.

### Движение и исходные данные

- `render` вызывается каждые **40 мс**, 25 кадров/с, согласно Дополнению.
- `view.c` отдаёт **64 логарифмические полосы 40…20000 Гц**, 0…255 = −72…0 дБ.
  UI объединяет соседние пары через максимум в **32 видимых столбика**. Менять
  уже согласованный ABI или присылать только 32 полосы не требуется.
- Каналы: до 32 значений 0…255, каждый канал — свой столбик. В превью есть 8, 18 и 32.
- Атака — 1800 единиц/с, спад — 380/с; пик удерживается 240 мс и опускается 220/с.
  Высота — до 26 точек. На паузе целевой уровень становится нулём, столбики затухают.
- Используется `nowMs`, целочисленная арифметика. Большой разрыв вызовов ограничен
  шагом 250 мс; повторный вызов с тем же временем не двигает огибающую.
- Время меняется раз в секунду; прогресс — только при изменении его пиксельной длины.
- Fade 0…15 за ~0,3 с делает обвязка. Отрисовка не управляет прозрачностью/платой.

Спектр APNG получен из локального `melodia.wav` в `E:\zx\Music\MIDI\…`:
PCM 8 кГц, Hann/FFT 2048, частотные полосы как в ABI, амплитуда нормирована в dBFS.
Файл обрывается раньше заявленной в заголовке длины: доступны **2,812375 с**, этот
реальный фрагмент зациклен для четырёхсекундного превью. Выше Найквиста 4 кГц уровни
нулевые. Полный путь и параметры — `previews/audio_source.json`.
Аудиофайл не копируется. Уровни каналов XM/VGZ — демонстрационный синтез.
Названия треков и обложка в превью вымышленные; чужих обложек/фрагментов аудио в
исходниках и данных тестов нет. APNG не содержит звук.

## Интерфейс с готовой обвязкой

```cpp
using pui_model_t = zm_ui_model_t;

namespace zifi::player_view {
constexpr uint16_t kWidth = 640, kHeight = 360, kCoverSide = 192;
struct Rect { uint16_t x0, y0, x1, y1; };
using Allocate = void* (*)(void* context, size_t bytes);
using Release = void (*)(void* context, void* pointer);
bool begin(Allocate allocate, Release release, void* context);
void end();
int render(const zm_ui_model_t& model, const uint16_t* cover,
           bool coverChanged, bool full, uint32_t nowMs,
           uint16_t* canvas, Rect* dirty, int maxDirty);
}
```

`begin` выделяет один кэш 460800 байт через переданный callback. Обвязка должна
разместить его в PSRAM. `end` освобождает его через `release`. Повторный `begin`
сначала освобождает старое состояние; нехватка памяти возвращает `false`.
Экземпляр один, вызовы последовательные; отрисовка не потокобезопасна.

`cover` — RGB565 192×192 либо `nullptr`; память принадлежит вызывающему.
`coverChanged` и `cover_serial` учитываются. JPEG, масштабирование 256→192,
получение модели, fade и передача в Tang остаются в существующей обвязке.

Прямоугольники полуоткрытые, оба x чётные. На полном обновлении — один 640×360.
При нехватке слотов последние области объединяются: изменённые точки не теряются,
но передаваемая площадь может увеличиться. Для обычного кадра достаточно 12 слотов,
в существующей обвязке их 32. При `maxDirty <= 0`, нулевом холсте/списке или до
успешного `begin` возвращается 0 без рисования.

Тексты читаются с ограничением длины массива, даже без завершающего нуля.
Счётчика изменений текстов в текущем `zm_ui_model_t` нет: вместо него считается
ограниченный хеш текстовых и статических полей. Хеш не захватывает спектр, время,
счётчики очереди или температуру. Обновление метаданных, обложки, состояния,
страницы и вида инициирует полную перерисовку; обычный кадр использует кэш.
Необходимых новых полей модели **нет**. Опциональное `text_serial` могло бы убрать
хеширование; сейчас оно не нужно для подключения.

Для будущего включения нужны `player_ui.cpp`, `fonts/pui_font.cpp`, их заголовки
и замена декларации `zifi/player_view.hpp` (в частности, kCoverSide=192). Старую
реализацию одновременно не линковать. `zm_app.h` берётся из настоящего SDK,
локальной копии ABI здесь нет. Само подключение в прошивку не выполнялось.

быть больше; это не ограничитель, который отбрасывает обновления.

точек по 99 неполным кадрам. Во всех демонстрационных последовательностях максимум
**8274**. Это сумма площадей возвращённых прямоугольников, включая выравнивание.
Не следует принимать тихий узкополосный WAV за наихудший случай. Сырые данные —
`build-pc/preview_metrics.csv`, сводка — `previews/render_stats.json`.

При оценке LINK 0,4…0,5 мкс/слово: 12000 точек = 6000 слов ≈ 2,4…3,0 мс;
полный холст 115200 слов ≈ 46…57,6 мс. Это расчёт по заданию, не измерение платы.
Цели CPU **4 мс обычный / 60 мс полный** ещё не подтверждены. В render нет ОС,
ESP-IDF, double, исключений, RTTI, STL и динамических выделений.

## Проверки этапа 1

На этапе 1 выполнены сборка превью clang, генерация артефактов и визуальный просмотр
PNG. Раскрытие RGB565 повторяет старшие разряды, как `ex5/ex6` в `fb_ovl.sv`.
Масштабирование только nearest neighbour ×2: ни сглаживания HDMI-картинки, ни
субпиксельного текста. Fade считается поканально с целочисленным floor:
`background + (overlay - background) * (alpha + 1) // 16`.
Фон WC нарисован для этого превью, не является снимком реальной Evo.

Палитра, собственный шрифт, обложка 192×192, компактный анализатор и многоточие
вместо бегущих строк утверждены пользователем. Предварительные оценки выше
относятся к этапу 1; актуальные размеры и оценка CPU приведены ниже.
Ни прошивки, ни соединения с платой, ни установки/скачивания не было.

## Этап 2

Выполнен 2026-10-21. Все сборки, логи и производные файлы — в `build-pc`.
Исходники Firmware читаются напрямую и не изменяются. Подключение к плате,
прошивка, установка инструментов и загрузки не выполнялись.

### Что изменено

- Буфер номера станции увеличен с 8 до 12 байт: GCC 15.2 выдавал
  `-Wformat-truncation`, считая возможным отрицательный `int`. Номер и его
  формат `%02d` сохранены. Первое сообщение — `build-pc/xtensa_initial_warning.log`.
- Полный кадр использует точные таблицы неизменного фона: 8192 байта оттенков
  RGB565 и 2000 байт координатных слагаемых, `constexpr`, во flash. Это убирает
  повторные деления, квантование и сбор dirty для каждой фоновой точки. Полный
  кадр по-прежнему возвращает один прямоугольник 640×360.
- Комментарий API уточнён: при нехватке слотов области объединяются в последнем
  доступном прямоугольнике, как и раньше.

Расчёт до оптимизации показывал риск ~151–168 мс на полный кадр. После неё —
~42–58 мс по той же модели стоимости, с погрешностью, описанной ниже.
Отрисовка всех 230400 точек фона сверена с исходной формулой. Повторно построены
**125 RGB565-кадров** (25 статических и 100 анимационных): каждый побайтно совпал
с этапом 1. Новые копии — `build-pc/stage2-preview/raw`, SHA-256 —
`build-pc/preview_stage2_hashes.json`. Утверждённые PNG/APNG в `previews` не
перезаписывались: заметных и скрытых пиксельных изменений в этих кадрах нет.

### Проверки на ПК

`tests/pui_stage2.cpp` выполняет длинную воспроизводимую последовательность
с фиксированным xorshift seed. Три независимо скомпилированных экземпляра
отрисовки получают одинаковые модели и время:

1. Основной экземпляр обновляет холст пошагово.
2. Эталон рисует **полный кадр на каждом шаге**, сохраняя собственную историю
   огибающей/пиков. Это существенно: новый `begin` на каждом кадре обнулил бы
   анимацию и дал бы неверный эталон.
3. Повторный экземпляр проверяет детерминизм и пикселей, и списка dirty.

На каждом шаге сравниваются все 230400 пикселей, проверяется покрытие каждой
изменившейся точки **объединением** dirty; отдельно копируются только dirty в
модель памяти Tang и проверяется её равенство полному эталону. Проверяются
чётность обоих x, полуоткрытые границы, количество прямоугольников и защитные
области холстов, кэшей, обложки и массива dirty. Вместимость dirty меняется
между 1, 2, 3, 8, 12 и 32.

Сценарии:

- 2048 непрерывных кадров спектра/времени и 6000 смешанных кадров: все страницы,
  виды и состояния, время, громкость, температура, очередь и ошибки декодеров;
- изолированные изменения каждого текстового поля, номера трека, обложки через
  `coverChanged`, через `cover_serial` и через наличие/отсутствие указателя;
- все 256 байтов CP866 во всех текстовых полях, включая незавершённые массивы,
  длинные строки, станции и пустые поля; `0x00` — конец строки, `0x01…0x1F` — `?`;
- каждый `count=0…255` для спектра, каналов и станций, `current=255`; включая
  значения больше 64, нечётное число полос и переполнение входных процентов;
- 0 мс, границы секунд/минут/часа, 1:02:45, 10/100 часов и `UINT32_MAX`,
  длительность 0/1/225000/3600000/`UINT32_MAX`; температуры −128…127 и пороги 70/75;
- 512 моделей со случайными сырыми байтами без предварительной санации обвязкой;
- повторные `nowMs`, переход `uint32_t` через ноль, большие промежутки времени;
- `begin/end`, повторный `begin`, отказ выделения, пустые callback/холст/dirty,
  `maxDirty=0/-1`; отсутствие выделений через callback во время кадров и
  освобождение единственного кэша.

Дополнительный `tests/pui_unit.cpp` проверяет 11 ожидаемых строк времени,
поведение всех байтов CP866 для трёх размеров шрифта и точность нового фона.
Обычная сборка clang 23.1.2 и сборка **AddressSanitizer** проходят весь набор;
ошибок памяти, отличий пикселей и непокрытых изменений не обнаружено.
Каждый прогон: **10873 кадра**, из них 2607 полных, 2987 непустых частичных,
5279 без изменения пикселей; проверено покрытие **131759805** изменений точек.
AddressSanitizer дополняет защитные области; проверка утечек ASan отключена,
баланс выделений callback проверяет сам стенд.

Логи: `stage2.log`, `stage2_asan.log`, `unit.log`, `unit_asan.log` в `build-pc`.
SHA-256 исходников и использованных файлов Firmware — `build-pc/stage2_inputs.json`.

### Сборка Xtensa и размеры

Компилятор из задания: `xtensa-esp32s3-elf-g++.exe`, GCC **15.2.0**,
`esp-15.2.0_20251204`. Оба исходника собираются без предупреждений с
`-O2 -Wall -Wextra -Werror -std=gnu++17 -mlongcalls -ffunction-sections
-fdata-sections -fno-exceptions -fno-rtti`. Дополнительно `-fstack-usage`
создаёт отчёты `.su`. Прошивка не линкуется и не изменяется.

Результат `xtensa-esp32s3-elf-size`:

| Объект в build-pc | text (код + const) | data | bss |
|---|---:|---:|---:|
| `player_ui_xtensa.o` | 25202 | 0 | 260 |
| `pui_font_xtensa.o` | 83958 | 0 | 0 |
| Сумма | **109160** | **0** | **260** |

Расшифровка `size -A`: инструкции `.text` **11911** байт, `.literal` **1368**,
`.rodata` **95881**. Итого код с литералами **13279** байт; const-данные
**95881** байт, в том числе шрифт **83958**, таблицы фона **10192**, остальные
строки/константы **1731**. Это ~106,6 КиБ flash суммарно, const-таблицы меньше
бюджета 150 КБ. `.bss` — 260 байт; дополнительный кэш остаётся **460800 байт
PSRAM**, выделяется только в `begin`. Холст и обложку предоставляет обвязка.

Это размеры объектных секций до финальной линковки, без служебных ELF-секций,
линкерного выравнивания и библиотек. Внешние зависимости: `memcpy`, `snprintf`,
`__udivdi3` и таблица шрифтов; прямых вызовов malloc/new, RTTI или исключений нет.
Наибольшие собственные кадры стека: `render` 672 байта, `drawMain` 624 байта;
это не полный стек задачи с библиотеками.
Подробности — `xtensa_size.log`, `xtensa_sections.log`, `xtensa_symbols.log`,
`xtensa_undefined.log`, `xtensa_disassembly.log`, `xtensa_totals.json` в `build-pc`.

### Время кадра на ESP32-S3 240 МГц

**Плата не измерялась.** Основной метод — счёт операций на ПК и приближённая
стоимость по дизассемблеру именно Xtensa GCC 15.2. Инструментированная копия
`player_ui.cpp` создаётся только в `build-pc`; код для ESP не содержит счётчиков.
`tests/pui_profile.cpp` считает вызовы рисования, фактические записи, точки
градиента/глифов, смешивание, хеширование, копирование и форматирование.
Сырые данные — `build-pc/profile.csv`, расчёт — `timing_estimate.json`.

Формула: `мс = (10000 + сумма(Nопераций × циклы)) / 240000`.
Принятые стоимости в циклах: put 18 + ещё 20 при изменении точки, dither 65,
табличный фон 14/точку, рисунок заглушки 40/точку сверх dither/put,
проверка скругления 15, восстановление 6/точку сверх put, выборка маски глифа 12,
смешивание 45 сверх put, хеш 6/байт, memcpy 2/пиксель, snprintf 1500/вызов.
10000 циклов на кадр — запас на управление, огибающие, обход строк и деление
прогресса. Для ориентира: до оптимизации фона отдельная функция dither имела
53 инструкции (сохранён `xtensa_disassembly_before_background_optimization.log`);
в итоговой сборке она встроена. Путь put — 11 без изменения / 27 с изменением,
плюс вызов, проверки и задержки памяти.
**Коэффициенты являются допущениями**, а не замером отдельных инструкций.

| Сценарий | Оценка CPU, среднее | Максимум в сценарии |
|---|---:|---:|
| Спектр 64 полосы + время, 1000 кадров × 40 мс | **3,40 мс** | **3,97 мс** |
| Чередование тишины/максимума каждые 400 мс, 1000 кадров | 2,12 мс | 4,30 мс |
| Полный главный экран с обложкой | **41,8 мс** | один замер счётчиков |
| Полный главный экран с процедурной заглушкой | **58,1 мс** | один замер счётчиков |

Ожидаемая точность грубая: **примерно ×0,5…×2**, это не доверительный интервал
и не гарантированная верхняя граница. Например, 3,40 мс следует читать как
порядок 1,7…6,8 мс; 41,8 — 21…84 мс; 58,1 — 29…116 мс. Не измерены промахи
кэша flash/PSRAM, конкуренция с аудиодекодерами и прерывания. При вытеснении
низкоприоритетной задачи реальное время до готового кадра может быть ещё больше.
Поэтому **лимиты 4/60 мс на аппаратуре пока не подтверждены**; стресс уже даёт
4,30 мс по центральной оценке. Эти цифры не включают передачу в Tang.

Есть и отдельный замер оптимизированного x64-кода на ПК (`benchmark.log`):
9 серий по 1000 обычных / 40 полных кадров, только render с подготовленными
входами, без сравнения холстов и передачи. Он показывает стоимость на этом ПК
и эффект оптимизации; простого переноса отношения частот x64→Xtensa здесь нет.
На Intel Xeon E5-2667 v4 (номинально 3,20 ГГц) медианы серий: **45,0 мкс**
обычный, **793,3 мкс** полный с обложкой, **1026,4 мкс** без неё.
Минимум/максимум средних по сериям: 44,9…57,0 / 783,4…884,5 /
1018,6…1035,5 мкс соответственно; это не максимальная задержка отдельного кадра.
До оптимизации полные кадры давали около 2077/2325 мкс на этом же ПК.

Если принять оценку LINK из задания 0,4…0,5 мкс/слово, тест Claude даёт передачу
0,935…1,169 мс в среднем, 1,582…1,977 мс на максимальном обычном кадре,
1,747…2,184 мс на скачущих полосах. Полный холст — 46,08…57,60 мс дополнительно
к CPU. Скорость LINK также не измерялась на плате.

### Как повторить

Из этой папки, без установки дополнительных зависимостей:

```powershell
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py
```

Запускает обычные тесты и бенчмарк, AddressSanitizer, тест обвязки, Xtensa/size,
проверку исходных превью и счёт операций. При любой ошибке завершается с ненулевым
кодом; подробности остаются в `build-pc`. Исходные `build-pc/raw`, `cover.rgb565`,
`spectrum.bin` и `preview_text.h` этапа 1 нужны для проверки неизменности дизайна.
В окружении сборок TEMP/TMP и рабочая папка указывают на `build-pc`; Python
не создаёт `__pycache__` в Firmware. Используется уже имеющаяся ASan DLL из LLVM.

Отдельные части:

```powershell
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py --only host
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py --only asan
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py --only overlay
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py --only xtensa
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py --only previews
& 'E:\zx\esp\pio-venv\Scripts\python.exe' .\tests\run_stage2.py --only profile
```

Полные команды компилятора записываются в соответствующие `build_*.log`.
Остаётся аппаратная проверка времени CPU/LINK в составе прошивки; интеграция
и прошивка, согласно заданию, выполняются отдельно владельцем обвязки.
