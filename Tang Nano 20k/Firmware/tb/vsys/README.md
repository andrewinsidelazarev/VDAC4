# Стенд Verilator ядра FT812 (`tb/vsys`)

Ядро FT812 слота 1 целиком, в замкнутом цикле с игрой: `ts_fb_core` как в `ts_fb_hdmi_top` с
`HAS_EVO = 0` (вывод 720p, SCALE, HDMI), SDRAM — потактовая модель, хост Evo — программа на C++.
Отвечает на вопрос, которого не видно в тестбенче одного кадра: сколько шагов в секунду делает
игра, которая ждёт смены листа (`REG_DLSWAP`), и сколько кадров доходит до экрана.

| файл | что |
|---|---|
| `vsys_top.sv` | `ts_fb_core` (CALIBRATE = 0, точка выборки SDRAM 1, flash чистая, ESP и BL616 молчат) + `sdram_cyc` + отводы замеров (смены листа, кадры растеризатора, буфер вывода); параметр `H_FP` — 110 (720p60, ядро FT812 с 1.20) или 440 (720p50); дерево с `rtl/sd_bridge.sv` (с 1.24) собирается с `VSYS_SD` — SDRAM на clk_sd 123,75 МГц (`SD_FAST`) |
| `sdram_cyc.sv` | SDRAM 64 Мбит × 32, BL 8, CL 2 или 3 (с `SD_FAST`), чтения конвейером — данные как у `tb/sdram_model.sv`, без проверок времени; память открыта C++ |
| `vsys_main.cpp` | клоки 61,875, 123,75 (clk_sd, фронты совпадают с clk_mem) и 74,25 МГц на общей шкале, SPI хоста 28 МГц (как Evo), развёртка FT812 1024×768@59, игра по трассе |

Сборка и прогон (Verilator 5 — `verilator_bin`, `VERILATOR_ROOT`; clang++):

```sh
scripts/run_vsys.sh build                                   # текущее ядро -> sim/vsys/cur/vsys.exe
scripts/run_vsys.sh build out/core_1.19 sim/vsys/v119_50 -GH_FP=440   # выпущенное ядро, вывод 50 Гц
sim/vsys/cur/vsys.exe --trace T.bin --hex frame_ramg.hex --no-skip --seconds 2
```

Список RTL берётся из `SRC` в `scripts/run_fb_sim.sh` того же дерева — так собираются и ядра из
`out/core_*`. Секунда модели — около 80 с счёта на одном ядре процессора; прогоны независимы и
идут параллельно.

## Игра

Трасса (`VTR1`): на шаг — такты Z80 (14 МГц) подготовки видео `t_v`, логики `t_l`, вывода `t_e`
и слова листа. Шаг, как у R-Type (`v30z80_runtime.asm`, `v30z80_host.asm`):

1. `HostVideoSkip`: `REG_FRAMES` по SPI; долг кадров развёртки → шаг без вывода (`--no-skip` —
   без этого, как Zuma Deluxe);
2. с выводом — `t_v`; затем логика `t_l` (смена прошлого листа идёт в это время);
3. с выводом — опрос `REG_DLSWAP` раз в 15 мкс до 0, лист в RAM_DL по SPI, остаток `t_e`,
   `REG_DLSWAP = 2`.

Первый шаг трассы — лист установки (ручки битмапов игры, если она задаёт их один раз).

Итог прогона: шагов игры в секунду (полная скорость — 59,08), смен листа, кадров растеризатора
и их время (FT_RTIME), кадров, взятых выводом, ожидание хоста на DLSWAP и задержка «запрос
DLSWAP → смена». `--dump F.hex` — в конце выводимый кадр FT из SDRAM (как `ft_frame.hex`
tb_ft_render; картинка — `scripts/ft_rtl_check.py frame`).

Ядра с 1.24 (`VSYS_SD`) — ещё такты растеризатора по причинам (`rc` в `vsys_top.sv`): доли
тактов исполнителя (точки, промах кэша текселей, палитра, сглаживание, ожидание обходчика,
подготовка задания, начало плитки — ждёт выгрузку…), слова листа на плитку и ожидание
обходчика, заполнения кэша и их задержка (приём заявки, данные); и число плиток 64×16,
изменившихся от прошлого объявленного кадра. Разбор по этим замерам —
`docs/ft812-render-speed.md`.

## Сверка с платой

Кадры R-Type, снятые с платы с ядром 1.19 (`ftdump`, FT_RTIME платы), стенд 1.19 с выводом 50 Гц:
кадры без лишних ручек — 16,3/17,3 мс (среднее/наибольшее) против 17,74 на плате, 17,5/18,6
против 18,7, 16,3/17,2 против 17,69, 15,9/16,7 против 17,28. Кадр Zuma Deluxe: 1.19 — 35 мс
(плата 31–38), 1.20 и 1.21 — 44–45 мс (плата 38–44 и 36–45).
