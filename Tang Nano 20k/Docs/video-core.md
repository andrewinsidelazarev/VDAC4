# Ядро видео: MJPEG AVI декодирует ПЛИС

Отдельное ядро Tang Nano 20K для плеера FTVIEW4: ролик MJPEG декодирует сама ПЛИС, а не BL616.
На BL616 (прошивка 34) кадр 512×384 шёл ~7 кадров/с. Пользователь отверг пропуск кадров
(«Давай ренднринг 24 к/с») и предложил «аппаратный 720p декодер отдельным слотом».

Состояние на 27.10.2026: ядро (RTL, сборка Gowin), приложение ESP VIDEO.ELF и режим ядра видео
в FTVIEW4 готовы и проверены на ПК. Первый запуск на плате (ядро из кэша BL616) — ядро через
0,5 с уходило в слот 0 (исправлено, см. «Возврат в слот 0»). Ядро встроено во flash Tang —
слот 3 (прошивка BL616 35, ESP 0.1.101): стоит на плате с 27.10.2026 18:27, `tang core load VIDEO`
поднимает ядро видео за 500 мс, оно держится до `tang boot` и возвращается в TS-Config.
Первый ролик через FTVIEW4 (ядро 1.34): звук шёл, экран чёрный, без панели. Причина — `hdmi_tx`
1.34 без защитной полосы видео HDMI: приёмник телевизора не находит начала строк (`tb_hdmi_tx`,
разбирающий поток по преамбулам и полосам, видит 0 строк; ядро FT812 1.34 так же давало чёрный
экран). Ядро видео **1.35** — с `hdmi_tx` 1.20–1.33 (как у TS-Config 1.32): на плате ролик идёт с
картинкой. Ролик 16:9 шёл «не на весь экран» (холст 4:3 с полями), 4:3 — «с вылетом за экран по
вертикали» (ядро не знало SIZE 95 % слота 0) — **1.36** (холсты 16:9), VIDEO.ELF 0.3 и FTVIEW4 с
фоновой таблицей перемотки. ESP 0.1.102 писала ядру видео CTRL с настройками слота 0 — запись
сбрасывала точку выборки чтения SDRAM (мусор на картинке) и растягивала 4:3 по ASPECT 16:9 до краёв
экрана; пользователь: прошивка ESP под отдельное приложение не меняется — ESP возвращена на
0.1.101. **1.37**: ядро видео само читает настройки слота 0 из flash Tang и берёт из них только
SIZE; ролик вписывается в экран в своих пропорциях, как JPG; записи CTRL с LINK не принимает
(на плате: «4:3 и 16:9 вписаны в экран, без глюков»).

Затем пользователь: «тормозит на некоторых видео», «широкоформатные видео обрезаются в 4/3»,
«иногда зависает и не выходит в slot0», «опустошение 32КБ FIFO — это при 8 МБ SDRAM?». Журнал
ESP показал обе причины. (1) Картинка вставала до 0,35 с («audio ahead of picture by 356 ms»):
медиа-FIFO 32 КБ в BSRAM — около одного кадра MJPEG, его опустошала любая пауза подачи с карты
Evo (шаг фоновой таблицы, задержка карты, проход FAT). (2) Ролик, который ядро видео не брало
(FTVIEW4 отдавал ядру только MJPEG до 1024×768 с ровно двумя потоками), уходил старым путём FT812
(BL616, CMD_PLAYVIDEO): экран FT812 4:3, кадр обрезан, декодирует медленно, а Tang остаётся в
слоте 1 (в журнале — «core 02 version 1.29», M_SEL=1). **1.38**: медиа-FIFO 2 МБ в SDRAM; кадр
больше 1024×768 (HD) — вдвое меньше, вписан в экран; звук — только дорожка 01wb, кадры — 00dc,
чужие дорожки пропускаются. FTVIEW4 (6d84) отдаёт ядру кадры до 2048×1536 и ролики с лишними
дорожками, фоновая таблица идёт шагами, пока в FIFO больше 256 КБ. VIDEO.ELF 0.4 — окно панели по
тем же правилам. 1.38, VIDEO.ELF 0.4 и FTVIEW4 6d84 стоят на плате с 27.10.2026 ~23:05.

Ролик «КИНО — Мама, мы все тяжело больны» (кадр 512×384, внутри — широкая картинка 512×222 с
чёрными полосами сверху и снизу) в 1.37–1.38 выходил окном 4:3 — узким, с полями по бокам
(«ни в какой версии этот ролик не вписывался нормально»). Пользователь: «В FT812 всё показывало
верно. Значит растягивай любое видео до пропорций, указанных в SLOT0». **1.39**: окно у всех
холстов — по ASPECT и SIZE слота 0, холст растянут на него, как кадр FT812 (при ASPECT 16:9 ролик
512×384 — во всю ширину экрана, как было на пути FT812). VIDEO.ELF 0.5 — панель в том же окне,
строки о подстройке синхронности звука — сводкой раз в 5 с (прежде забивали весь журнал ESP).
На плате с ~23:45 — пользователь: «Работает». Но: ASPECT 4:3, выставленный за 1,5 с до ролика, не
действовал, и после выхода TS-Config снова был 16:9. Журнал ESP: 4:3 виден в 960,5 с, ядро видео
грузится в 961,95 с, а прошивка ESP пишет изменение во flash, лишь когда оно продержалось до
следующего опроса (раз в 2 с) — не успела, ядро и TS-Config прочли из flash прежнее. Ошибка общая
для всех ядер, которые грузит ESP (Next, NES, видео). **ESP 0.1.103** (`ec2f0e8b…`, собрана, не
на плате): `tang_flash::flush()` перед BOOT слота и загрузкой из кэша BL616 (`core_store.cpp`) —
несохранённые настройки TS-Config пишутся во flash сразу. Переход в ядро FT812 по M_SEL делает сам
TS-Config — там окно 2–4 с остаётся. ESP 0.1.103 на плате с ~23:55; пользователь, 27.10.2026:
**«Всё работает»** (ядро 1.39, VIDEO.ELF 0.5, FTVIEW4 6d84, ESP 0.1.103).

## Части

```
Evo: FTVIEW4.WMF ─ банк ядра видео (стр. 11) ─┬─ SPI FT812 ─► ядро видео Tang (слот 3 flash)
                                              │               MJPEG → кадр → HDMI 720p50
                                              │               звук NNwb → FIFO звука ─┐
                                              └─ ZiFi SPI ──► ESP: VIDEO.ELF ◄── LINK ┘
                                                             ЦАП ESP (PCM, MP3), панель и окна
                                                             оверлеями Tang
```

| Часть | Где | Что делает |
|---|---|---|
| Ядро видео | `fpga/vdac2`, `ts_fb_core` с `HAS_VIDEO = 1` → `impl/pnr/ts_fb_video.fs` | разбор AVI, декодер JPEG, темп кадров, вывод 720p, FIFO звука для ESP, оверлеи |
| VIDEO.ELF | `VDAC4/Tang Nano 20k/Cores/VIDEO/esp` | грузит ядро (слот 3 flash Tang), играет звук на ЦАП ESP в такт картинке, рисует панель плеера, список и сообщения |
| Переход в слот 3 | прошивка BL616 35 (`UNDERRUN VDAC4/app-bl616`: `core_jtag_boot`, команда BOOT ящика), ESP 0.1.101 (`core_store.cpp`, `core_cache_client.cpp`) | ESP проверяет начало битстрима в слоте, BL616 по JTAG переводит ПЛИС в слот 3 |
| FTVIEW4 | `VDAC4/Tang Nano 20k/FTVIEW4`, банк 11 (`src/core.c`) | ESP и ядро, поток файла в FIFO ядра, клавиши, пауза, перемотка, список роликов |

## Ядро

`ts_fb_core` с `HAS_EVO = 0`, `HAS_FT = 0`, `HAS_VIDEO = 1` (`ts_fb_hdmi_top`, сборка
`scripts/gowin_fb_video.tcl`):

```
Evo ── SPI FT812 ──► ft_spi ──► vp_core: регистры FT, медиа-FIFO 2 МБ (SDRAM, с 1.38)
                                vp_avi: чанки AVI → слова JPEG; 01wb → FIFO звука (1024 слова)
                                jpeg_core (third_party/core_jpeg)
                                vp_fbwrite: холст → кадры FT в SDRAM
                                vp_pace: темп по выходным кадрам, пауза
SDRAM ◄── sdram_burst (метка 101, место растеризатора FT812)
  └──► fb_core (кадры FT) ──► fb_scanout (FT_W512) ──► fb_ovl (оверлеи ESP) ──► HDMI 720p50
ESP ── LINK ──► регистры звука, окно FIFO звука, оверлеи
```

- Хост — Evo по тем же выводам SPI, что у FT812 (`ft_spi`: SCK до 28 МГц, MISO на полтакта
  раньше).
- Кадры — три кадра FT `fb_core`, как у растеризатора FT812. Пока выводится один, пишется
  другой.
- Вывод — 720p50 (VIC 19), как у TS-Config. 25 кадров/с — ровно по два выходных кадра.
  Окна ASPECT/SIZE те же, что в слоте 0: 4:3 или 16:9 и размер 100/95/90 % для старых
  приёмников HDMI. С 1.37 ядро читает их из flash Tang само, как TS-Config после сброса (`fb_flash`
  без моста для ESP: FLASH_STATUS для LINK — 0, ESP не сохраняет и не пишет настройки ядру
  видео). С 1.39 окно у любого холста — по ASPECT и SIZE, холст растянут на него, как кадр FT812
  (в 1.37–1.38 бралось только SIZE, окно шло в пропорциях холста). Записи CTRL с LINK ядро видео
  не принимает. Стенд `vvid --settings 1 1` (во flash — 16:9 и 95 %): все холсты — окном
  1216×684; `--settings 0 1` — окном 912×684.
- SDRAM — на clk_mem (61,875 МГц), как у TS-Config.
- Личность ядра (LINK 0x01, старший байт) — **05**; UserCode битстрима — `0x56443405`
  (метка VDAC4 для кэша ядер BL616; 03 — Next, 04 — NES).
- Возврат в слот 0 — как у ядра FT812: `M_SEL = 0` и 500 мс без обмена по SPI → BOOT, но только
  после первого обмена хоста с ядром. Ядро FT812 включает первый же обмен Evo, а ядро видео
  грузит ESP, пока плагин ждёт его готовности: без этого условия ядро через 0,5 с после загрузки
  уходило в слот 0 (так было на плате 27.10.2026). До первого обмена ядро стережёт VIDEO.ELF
  (молчание плагина > 2 с — назад в слот 0). Плагин ставит `M_SEL = 1`, как только ядро
  заработало, и держит до выхода.

### Слот 3 flash Tang

Flash Tang (XT25F64B, 8 МБ):

| Адрес | Что |
|---|---|
| 0x000000 | слот 0 — TS-Config (переход multiboot — в слот 1) |
| 0x100000 | слот 1 — ядро FT812 (переход — в слот 0) |
| 0x200000 | слот 2 — шрифты ПЗУ FT812 (VD4FONT1, 286 КБ; ESP переписывает их в SDRAM после каждой загрузки ядра FT812) |
| 0x300000 | **слот 3 — ядро видео** (`ts_fb_video.bin`, 886 КБ, переход — в слот 0) |
| 0x400000…0x6FFFFF | слоты 4…6 свободны |
| 0x7FF000 | сектор настроек кадрового буфера |

Multiboot ведёт только по адресу перехода из заголовка битстрима (команда D2), и из слота 0 —
только в слот 1. Адрес перехода ПЛИС запоминает из того потока настройки, который пришёл
последним, — из flash или по JTAG: ядро из кэша BL616 (адрес 0) по Reconfig уходит в слот 0, а
не в слот 1, куда вёл заголовок TS-Config. Поэтому BL616 (прошивка 35, `core_jtag_boot`) стирает
SRAM ПЛИС, по JTAG шлёт **только заголовок** битстрима (64 байта: преамбула, A5C3, IDCODE, слово
загрузки, ключ сжатия, защита, D2 с адресом 0x300000, INIT_ADDR — байт в байт как у ядер VDAC4),
без кадров, и делает Reconfig — ПЛИС грузит битстрим слота 3 из flash. Назад — как у ядра FT812:
ядро просит BOOT, BL616 делает Reconfig, адрес перехода ядра видео — 0.

Команда ящика BL616 — **BOOT** (`core_mailbox.h`, 9): слово 1 — адрес слота (кратен 0x100000,
меньше 0x700000), ответ LOADING, через 50 мс — переход. Ядро слота BL616 ведёт, как ядро из
кэша; снимков STATUS нет 3 с (слот пуст, битстрим испорчен) — назад в слот 0 тем же переходом по
адресу 0 (обычный Reconfig взял бы адрес слота снова). Прошивка до 35 отвечает BAD_CMD.

ESP 0.1.101 (`core_store::load`): у ядра «VIDEO» свой слот (`kFlashCores`: слот 3, личность 05).
ESP читает 128 байтов слота мостом к flash (ядро TS-Config) и проверяет синхрослово, IDCODE и
адрес перехода 0; годно — снимает SD Tang, шлёт BOOT и ждёт ядро на LINK (до 15 с): личность не
05 — назад в слот 0. Слот пуст, моста нет или BL616 старше 35 — как прежде: CORES/VIDEO.BIN с SD
Tang через кэш BL616. Сетевая консоль: `tang core load VIDEO`.

Запись слота — по слову пользователя, только через ESP:
`tools/tang_tool.py update --slot 3 <IP> fpga/vdac2/impl/pnr/ts_fb_video.bin`.

### Хост: регистры (адреса FT81x)

Для плагина ядро — FT812 с одним медиа-FIFO: DMA блока в окно FIFO, затем REG_MEDIAFIFO_WRITE.
Команд сопроцессора нет.

| Адрес | Что |
|---|---|
| 0x302000 REG_ID | чтение — 0x7C |
| 0x302020 REG_CPURESET | бит 0 — сброс потока: FIFO пуст (указатели 0), разбор, декодер, темп — с начала, эпоха звука + 1. Пока 1, поток стоит. Бит 2 — пауза: темп стоит, кадр на экране не меняется (у FT812 это сброс аудиодвижка; плагин пишет его только ядру видео). Чтение — {бит 2 пауза, бит 0 сброс} |
| 0x309014 REG_MEDIAFIFO_READ | позиция чтения FIFO (байт); слово защёлкивается при чтении младшего байта |
| 0x309018 REG_MEDIAFIFO_WRITE | позиция записи; применяется при записи старшего байта — когда принятые до неё слова уже в SDRAM |
| 0x0E0000…0x2DFFFF | окно данных FIFO (2 МБ): плагин пишет блоки по позиции записи, подряд по кольцу, словами |
| 0x000000…0x00003F | блок состояния, 32-битные слова (ниже) |

Блок состояния:

| Слово | Что |
|---|---|
| 0 | «VID1» (0x31444956) — это ядро видео |
| 1 | размер FIFO, байтов (2 097 152; до 1.38 — 32768) |
| 2 | слотов темпа с сброса: номер кадра ролика с повторами — время |
| 3 | объявлено кадров |
| 4 | отменено кадров (битые, сторож) |
| 5 | {высота, ширина} холста последнего кадра |
| 6 | мкс на кадр (avih) |
| 7 | {вставок стандартных DHT, 10 нулей, запись не подряд, приёмник переполнялся, пауза, FIFO пуст, запись занята, сброс} |

### Медиа-FIFO в SDRAM (1.38)

2 МБ с адреса слова 0 — место RAM_G FT812, которой в ядре видео нет (кадры FT — с 0x080000).
Прежний FIFO — 32 КБ в BSRAM — держал около одного кадра MJPEG (40–130 мс): любая пауза подачи с
карты Evo опустошала его, и картинка вставала (на плате 27.10.2026 — до 0,35 с). Теперь запас —
секунды, BSRAM занято 35 из 46 (было 46 из 46).

- Приём: байты хоста собираются в слова (по старшему байту) и ложатся в приёмник — 512 слов
  (один BSRAM). Из него слова уходят в SDRAM пакетами от `sw` до конца группы из 8 слов; слова
  группы вне пакета — маской 0 (DQM), поэтому неполная группа дописывается без порчи. Приёмник
  держит 2 КБ — ~0,6 мс SPI на 28 МГц; разъём SDRAM освобождается много чаще. Переполнится —
  слово теряется, флаг в слове 7.
- Объявление: REG_MEDIAFIFO_WRITE видна разбору, только когда все принятые до неё слова (и
  неполная группа) уже в SDRAM.
- Чтение: выборка наперёд — 32 слова (BSRAM), пакеты от `fw` до конца группы или до объявленной
  позиции; разбору — байт за байтом (до байта за 2 такта, как прежде).
- Разъём SDRAM ядра видео (метки растеризатора: запись 101, чтение 100) делят приёмник (первым:
  хост ждать не умеет), выборка и запись кадров `vp_fbwrite` — по одному запросу. Маска слов
  записи этого разъёма (`rd_wmask`) — новая в мультиплексоре `ts_fb_core`; у растеризатора FT812
  она всегда F.
- Сторож считает прогрессом только записи кадров: подача хоста не держит битый кадр.

Стенды: `tb_vpc` с моделью SDRAM (чтение, маска, изредка занятость до 600 тактов) и блоками хоста
случайной длины, кратной 4; сборка `-GFIFO_AW=10` (FIFO 4 КБ) — кольцо оборачивается сотни раз;
`vvid` — через настоящий `sdram_burst` и арбитр `ts_fb_core`.

### LINK (ESP)

| Слово / байт | Что |
|---|---|
| 0x0A / 0x028 | слотов темпа |
| 0x0B / 0x02C | {ширина холста, отменённые кадры} |
| 0x10 / 0x040 | CTRL настроек: [14] 16:9, [16:15] размер 100/95/90 % |
| 0x40 / 0x100 | чтение — {эпоха[31:24], пауза[23], слов FIFO звука записано[10:0]}; запись — слов прочитано ESP (AU_RP) |
| 0x41 / 0x104 | AU_CTL: [0] приём звука, [1] темп по часам звука, [15:8] подтверждённая эпоха |
| 0x42 / 0x108 | AU_CLK: время проигранного звука, мкс (для [1]) |
| 0x800… / 0x2000… | окно FIFO звука, 1024 слова: младший байт — первый |
| 0x30…0x37 / 0x0C0… | оверлеи fb_ovl: CTRL (бит 2 — режим 4 бит, 1.42), POS, SIZE, BASE; холсты — окно 0x80000… |
| 0x38 / 0x0E0 | OVL_PAL (1.42): [15:0] RGB565, [20:16] непрозрачность 0…16, [27:24] номер цвета, [28] оверлей |

### Разбор AVI (`vp_avi`)

Чанки читаются подряд. RIFF и LIST дают только заголовок и тип, их содержимое идёт теми же
чанками.

- `avih` — первое слово, мкс на кадр.
- `00dc`, `00db` — кадр JPEG: байты идут в декодер словами по 4. Пустой чанк — повтор кадра:
  слот темпа без кадра.
- `01wb` — звук (первая звуковая дорожка, её формат VIDEO.ELF берёт из первого strf «auds»):
  при включённом приёме (AU_CTL [0]) байты по 4 в FIFO звука, иначе мимо. FIFO полон или эпоха
  не подтверждена — разбор ждёт.
- Остальное (JUNK, idx1, strh, strf, с 1.38 — и чужие дорожки: `02wb`, `01dc` …) пропускается.
  До 1.38 брались любые NN: вторая звуковая дорожка шла бы в FIFO звука вперемешку с первой.
  Нечётный размер — байт выравнивания.

Кадр без DHT (камеры, «AVI1») декодируется стандартными таблицами K.3, как у FT812: перед байтом
DA вставляются 420 байтов `rtl/vp_dht_std.svh` (генератор `scripts/gen_vp_dht.py`).

### FIFO звука и эпоха

1024 слова (2 BSRAM), запись — clk_mem, чтение — SCK LINK. Сброс потока (REG_CPURESET) обнуляет
указатель записи и увеличивает эпоху; пока ESP не подтвердит её (AU_CTL [15:8]), звук ждёт —
иначе старый указатель чтения ESP испортил бы счёт. ESP читает FIFO всегда, пока приём включён:
полный FIFO держит разбор, а с ним и картинку.

### Запись кадра и холст (`vp_fbwrite`)

Точки декодера собираются в плитки 16 × 16 строк (4:2:0) или 16 × 8. Строка плитки — пакет
SDRAM из 8 слов. Холст — наименьший из 512×384, 640×480 и 1024×768, куда входит картинка: по
центру, по x — с шагом 16 точек, поля чёрные. С 1.36 широкая картинка (9·ширина ≥ 14·высота, до
576 строк) — на холст 16:9 той же ширины: 512×288, 640×360 или 1024×576. Развёртка (1.39) выводит
любой холст окном ASPECT/SIZE слота 0: шаг по x — как у холста 4:3 той же ширины, по y у холста
16:9 — 2/5, 8/19, 4/9 (288 строк), 1/2, 10/19, 5/9 (360), 4/5, 16/19, 8/9 (576). Стенды: `tb_vp` (холсты 512×288 и 640×360, 39 кадров), `scripts/run_ft_scan_video.sh`
(`tb_ft_scan` против `ft_scan_check.py video`, все холсты и размеры; на 1.39 — 12 случаев из 12,
расхождений нет).

С 1.38 картинка больше 1024×768 — вдвое меньше: берутся точки с чётными x и y (HD 1280×720 →
640×360 — холст 640×360 целиком, 1920×1080 → 960×540 на холсте 1024×576), плитка — вдвое ниже
(8 строк у 4:2:0, 4 у остальных; её дают 2 или 4 MCU подряд). Прежде FTVIEW4 отдавал такой ролик
пути FT812 — экран 4:3, кадр обрезан, медленно. Декодер успевает: кадр 1280×720 4:2:0 —
1,97 млн тактов (31,9 мс на 61,875 МГц), 1100×400 4:4:4 — 22 мс; 1920×1080 — ~70 мс (14 к/с,
ролик пойдёт медленнее). Подача с карты Evo для HD — отдельный предел: кадр HD — 60–160 КБ.
Стенд `tb_vpc` поток `hd` (make_vp_avi.py): 1280×720 4:2:0, 1296×730 4:2:2 (не кратен 16),
1100×400 4:4:4 — точка в точку с эталоном tb_jpeg через одну.

### Темп (`vp_pace`)

Каждый выходной кадр (50 Гц) добавляет 20 000 мкс к запасу. Слот ролика выходит, когда запас
дошёл до периода из avih: сразу после начала выходного кадра, и `fb_core` показывает его с этого
же кадра. 25 кадров/с — по два выходных кадра, 24 — по два и раз в 12 кадров три; кадры не
пропускаются никогда. Первый кадр выходит сразу; запас ограничен двумя периодами. Пауза
(REG_CPURESET бит 2): слоты не выходят, запас не растёт — после паузы темп с того же места.

Есть и темп по часам звука ESP (AU_CTL [1]), но VIDEO.ELF его не включает: если звук лежит в
файле позже своих кадров дальше, чем разбор опережает показ, часы встали бы навсегда.

### Сторож

Кадр в работе не продвигается ~68 мс, хотя данные есть: кадр битый (обрыв, прогрессивный JPEG,
DRI). Декодер сбрасывается, кадр отменяется, остаток чанка пропускается. Пустой FIFO — не сбой.

| Команда | Запрос | Ответ |
|---|---|---|
| 70 START | [имя ядра, 0] | F0 [1 — грузим] |
| 72 STATUS | [1][флаги][кадр начала LE32][кадров LE32][мкс на кадр LE32][байтов звука до начала LE32][имя, 0] или пусто | F2 [состояние][VERSION LE32][слотов LE32][отменено LE16][звук][ошибка, 0] |
| 73 EXIT | — | F3 [1] |
| 76 HDR | [смещение LE32][последний][байты заголовка до movi] | F6 [1] |
| 77 LIST | [показ][всего][первая][выбор][текущий — LE16][сообщение, 0][строки, 0…] | F7 [1] |
| 78 MSG | [вид 0/1/2][заголовок, 0][строка, 0][строка, 0] | F8 [1] |

Состояния: 0 — ждёт START, 1 — грузит ядро, 2 — работает, 3 — вернулись в слот 0, 255 — ошибка.
Флаги: 1 пауза, 2 панель, 8 перемотка. Плагин молчит дольше 2 с (60 с, пока на экране окно
списка или сообщения) — ядро назад в слот 0.

- **Ядро.** START → `core_load("VIDEO")`: из слота 3 flash Tang (ESP 0.1.101, BL616 35; слот
  пуст — CORES/VIDEO.BIN с SD Tang через кэш BL616). Личность 05 — иначе назад. До «работает»
  приложение включает приём звука ядра.
- **Звук** (`audio.c`). FIFO ядра → кольцо 2 МБ PSRAM → PCM 8/16 бит (здесь) или MP3 (декодер
  MP3.ELF плеера, с 0.6 вкомпилирован в VIDEO.ELF)
  → `pcm_write`. Формат — из HDR (strf). Ведущий — темп ядра: время картинки — (кадр начала +
  слот − 1) · период + время с выхода слота, в мкс; время звука — байты до начала потока +
  отзвучавшие кадры. Расхождение > 30 мс (после начала и паузы — > 8 мс): звук позади —
  выбросить входящее (не больше принятого сверх 60 мс: звук, лежащий в файле позже своих кадров,
  играет с опозданием, но без дыр), впереди — тишина. Кольцо полно — выбрасывается самое новое,
  с меткой разрыва. Пауза — по биту паузы ядра (LINK 0x40 [23]) и флагам плагина.
- **Панель и окна** (`hud.cpp`). Как у FTVIEW в масштабе 720p, в точках вывода (с 0.8): панель
  960×64 (шрифт 16) у низа окна картинки — полоса хода, время, «… ESP DAC», подсказки (флаг 16
  STATUS — вместо них текст из поля имени, «Indexing NN%»); окно 780×616 (окно FTVIEW ×0,9375) —
  список роликов (шрифт 24, строки через 30) или сообщение. Шрифт pui_font (CP866). Оверлеи — в
  режиме 4 бит ядра 1.42: у окна палитра «прозрачно, фон (13/16), полоса выбора, текст на фоне —
  4 ступени сглаживания, текущий (оранжевый) — 3, серый — 3, белый на полосе — 3», у панели — фон
  (12/16), дорожка, ход, текст — 4, серый — 3; цвет ступени — смесь фона и текста. До 0.8 окно было
  холстом 390×308 RGB565 ×2 со шрифтом 13, и прозрачность была на весь оверлей вместе с текстом —
  на телевизоре «мутно» (пользователь, 28.10.2026). Ядро старше 1.42 — панели и окон нет. Окно картинки — по SIZE из CTRL и размеру кадра из avih:
  широкий кадр — окном 16:9, как его выводит ядро 1.36; с 0.4 остальные — окном 4:3 при любом

## FTVIEW4: режим ядра видео

`VDAC4/Tang Nano 20k/FTVIEW4`: банк 11 (`src/core.c`), обмен с ESP — `src/esp_link.asm`
(proto.asm и zifi_spi.asm сетевых плагинов VDAC4, копия в `vendor/vdac4`, приём до 256 байтов).
Вход — шлюз `core_try` из банка изображений (crt0.s), до GS и FT812:
1. разбор заголовка: MJPEG до 1024×768, звук любой;
2. ESP, VIDEO.ELF из `/WC/ESP` на карте Evo — в кэш ESP (MOD_QUERY, если нет или изменился — MOD_PUT
   и MOD_COMMIT), APP_START (до FTVIEW4 a14f — CORE_APP, VIDEO.ELF с SD Tang), START, STATUS до «работает» (до 60 с; окна на это
   время нет — ядро из слота 3 встаёт за доли секунды), `M_SEL = 1`, REG_ID и «VID1»;
3. HDR, REG_CPURESET 1, STATUS с началом потока, REG_CPURESET 0, подача файла до конца movi
   (кэш SD — страницы 1…7, страница 8 — секторы idx1);
4. STATUS раз в 5 тиков WC; Space — пауза (бит 2); ←/→ — 10 с по таблице idx1 (страницы 12…15:
   у ядра нет RAM_G), Home — с начала; Enter и конец ролика — список (банк списка читает каталог,
   имена в CP866, рисует ESP); PgUp/PgDn — соседний файл; Esc — EXIT, слот 0, APP_STOP, текст WC.

**Таблица перемотки — в фоне** (`src/core_bg.c`, банк списка: в банке ядра нет места). Прежде она
строилась при первой перемотке целиком, с окном ESP «Building seek index...» 780×616 (пользователь:
«кто мешает построить в фоне? зачем это уродливое сообщение?»). Ролик лежит на карте Evo — idx1
читает Evo, не ESP. С открытием ролика банк ядра зовёт LIST_OP_BG_START, затем — короткие шаги
LIST_OP_BG_STEP (до 16 секторов idx1 или 255 кластеров цепочки, ~20 мс), когда FIFO ядра не берёт,
а кэш потока полон, и подряд — на паузе. Поток ролика и читатель idx1 — на одном потоке WildDOS:
шаг сохраняет его позицию (NSDC/EOC #3848, LLHL/LTHL #3860…#3867, CUHL #38A8 — по ним LOAD512
продолжает чтение), ставит свою и возвращает — без нового прохода FAT. Перемотка берёт готовую
часть таблицы (`BG_FAR` по #FE40 страницы 1: состояние, шаг, записей, процент); цель дальше —
таблица достраивается подряд, в панели ESP вместо подсказок — «Indexing NN%» (STATUS: флаг 16,
текст в поле имени). Тесты: `tests/test_core.py` — Right сразу (ожидание с процентами), Right
после готовой таблицы (без ожидания), файл с перемешанной цепочкой кластеров по 1 КиБ; во всех —
поток до перемотки байт в байт файл, поток после — с записи таблицы. Модель WC в тестах ведёт
позицию потока в тех же переменных WildDOS.

Нет ESP, VIDEO.ELF или ядра, не тот ролик — шлюз возвращается, и ролик играет прежний путь
(FT812/BL616).
