# A3.1 — кадровый буфер: TS-Config → HDMI 720p50

2026-09-25. Исходники — [fpga/vdac2](../Firmware/README.md), верхний модуль `ts_fb_hdmi_top`.
Вторая прошивка видеотракта рядом с [генлоком](a3-fpga-video.md): выход тактируется
кварцем Tang, и развёртка — настоящий стандарт, а не «близко к стандарту».

## Что делает

| | Генлок (`ts_hdmi_top`) | Кадровый буфер (`ts_fb_hdmi_top`) |
|---|---|---|
| Выходной режим | 896×640, 28 МГц, 31,25 кГц, **48,83 Гц** | **1280×720p50 CEA-861** (VIC 19): 1980×750, 74,25 МГц, **50,000 Гц**; картинка на всю высоту, 4:3 или 16:9 (ниже). Сборка с HD = 0 — 720×576p50 (VIC 17/18) точка в точку |
| Источник выходного клока | PCLK Evo | кварц Tang 27 МГц |
| Задержка | меньше строки | до ~1 кадра (в среднем ~15 мс) |
| Если PCLK пропал | выход гаснет | развёртка идёт, держится последний целый кадр |
| Разница частот кадров | нет (выход = вход) | повтор кадра примерно раз в 42 кадра (0,85 с) |
| Память | 2 строки в BSRAM | 3 кадра в SDRAM (3,375 МБ, с 0x4A0000 до конца; ниже — RAM_G и ПЗУ FT812, оверлеи ESP) |

## Как устроен

```
PCLK 28 ─ PLL ×2 → 56 МГц: ts_mux_capture → fb_capture ─┐ async FIFO (256 × 33 бит)
кварц 27 ─ rPLL ×5 → 135 МГц TMDS                        ▼
            ├ CLKOUTD ÷2 → 67,5 МГц: fb_core ⇄ sdram_burst ⇄ SDRAM (3 кадра)
            └ CLKDIV ÷5  → 27 МГц: fb_scanout ← fb_line_ram (2 строки) → TMDS → HDMI
```

- **Захват** — тот же `ts_mux_capture`, что у генлока: две фазы мультиплексора → пиксель
  {PAL_SEL, B5, G5, R5}. `fb_capture` вырезает окно 720×576 и пишет в FIFO заголовок строки
  и пары пикселей. Палитра применяется только на выходе — в памяти ничего не теряется.
- **SDRAM** — свой контроллер `sdram_burst`: пакеты по 8 слов (32 байта), автопредзаряд,
  регенерация каждые 7,8 мкс. Имеющийся `sdram.v` побайтовый (~50 МБ/с) — для кадров мало;
  нужно ~82 МБ/с (запись 48,83 кадра/с + чтение 50 кадров/с).
- **Тройная буферизация** (`fb_core`): писатель пишет кадр в буфер W; целый кадр становится
  «последним готовым» L; вывод в начале каждого кадра берёт L. Писатель никогда не пишет
  в выводимый буфер, поэтому разрывов нет. Кадр со сбоем (пропущенные строки, обрыв
  PCLK) не публикуется.
- **Вывод** (`fb_scanout`): строка L запрашивается за две строки до показа (~37 мкс
  на выборку, реально нужно ~10–20 мкс), приходит в двухстрочный буфер.

## Масштаб 720p: ASPECT, SIZE и сглаживание

В 720p кадр Evo 720×576 растягивается по центру кадра 1280×720 (`fb_scanout`, SCALE). Два пункта
меню (плагин WC через ESP; LINK — CTRL биты 14 и 16:15; хранятся во flash Tang):

| SIZE \ ASPECT | 4:3 — пропорции сохраняются | 16:9 — на всю ширину |
|---|---|---|
| 100 % (по умолчанию) | 960×720 (x 160) | 1280×720 |
| 95 % | 912×684 (x 184, y 18) | 1216×684 (x 32, y 18) |
| 90 % | 864×648 (x 208, y 36) | 1152×648 (x 64, y 36) |

SIZE 95 и 90 % — для телевизоров, обрезающих края кадра (overscan): у старых LG «Just Scan»
для 720p нет, а кадр 720p с картинкой на всю высоту телевизор растягивает за края (на карте
видеозахвата те же 720 строк видны целиком). Все размеры делят 720 и 576 нацело.

**Сглаживание по площади.** Множители дробные (×1,25 по высоте, ×1,33 или ×1,78 по ширине), и
ближайшая точка давала точки Evo неодинакового размера («пикселизация»: строки по 2 и 3).
Теперь точка вывода берёт цвет тех точек Evo, которые она накрывает, пропорционально площади:
внутри точки Evo — чистый цвет, на границе — смесь в пропорции; на глаз все точки Evo
одинаковые, а размытия, как у билинейного масштаба, нет. Точка вывода k занимает
[k·N/D, (k+1)·N/D) точек источника (N/D = 720/ширина, 576/высота); если она заходит за границу,
вес следующей точки — (acc + N − D)/N, с шагом 1/16. Счётчики (DDA) ведут и номер точки, и acc.

Для этого буфер строк — четыре блока BSRAM (`fb_line_ram`): чётные и нечётные строки × чётные и
нечётные точки, на четыре строки; за такт читаются четыре точки 2×2. Строка Evo
запрашивается из SDRAM, когда она впервые понадобится строке вывода (как основная или как
нижняя для смешивания), за две строки до показа — по-прежнему одна строка за раз и один раз за
кадр, нагрузка на SDRAM та же (77 760 чтений за симуляцию, как без масштаба). Палитра — у каждой
из четырёх точек, смешивание по ширине и по высоте — двумя ступенями конвейера. Проверка
испытательной таблицы и калибровка SD READ сверяют исходную точку из памяти — работают в любом
масштабе. Смена ASPECT и SIZE вступает с нового кадра (геометрия защёлкивается за 4 строки до
его начала, до первых запросов его строк).

## FRAME BLEND: среднее двух кадров (ядро 1.32, только TS-Config)

Классические демо дают лишние цвета мерцанием: кадры A и B идут через один (гигаскрин,
мультиколор с переключением экранов). На ЭЛТ глаз усредняет их в ровный цвет; на ЖК-телевизоре
видно мерцание 25 Гц, а повтор кадра раз в ~42 (48,83 → 50 Гц) ещё и сбивает чередование —
картинка дёргается раз в 0,85 с. FRAME BLEND (галочка в меню ESP, CTRL 17, по умолчанию
выключена) выводит **среднее двух последних целых кадров Evo**: пара (A, B) даёт (A + B) / 2, и
повтор кадра ничего не меняет — пара та же.

- **Четыре буфера** (`fb_core`, AVG): четвёртый кадр Evo — с адреса 0 SDRAM, на месте RAM_G FT812
  (в ядре TS-Config без FT812 её нет). Вывод на начало кадра берёт пару (latest, кадр перед ним),
  писатель пишет вне этих двух и выводимой пары. Если за один выходной кадр пришли два входных и
  свободного буфера нет, писатель пишет поверх старшего кадра пары — следующий выходной кадр
  выводится без смешения.
- **Строка пары читается дважды**: строка второго кадра — во временный буфер (BSRAM 512 × 32),
  затем строка первого; каждое слово смешивается при записи в строчный буфер. Развёртка, масштаб
  и палитра не меняются: смешанная точка пишется как {PAL_SEL = 1, B, G, R}.
- **Смешиваются только различающиеся точки**; одинаковые в двух кадрах проходят как есть — статичная
  картинка точно та же, что без FRAME BLEND. Среднее — **по яркости**, по каналам, таблицей
  4096 × 5 бит (`fb_avg_rom`, `scripts/gen_avg_tab.py`, гамма 2,2): чёрный с белым дают 184, как
  на ЭЛТ, а не 128 (простое среднее кодов). Точность — 5 бит на канал (шаг 8).
- **Чего не лечит**: мерцание с периодом 3 кадра (RGB-режимы демо) — останется рябь; в играх
  быстрые спрайты дают полупрозрачный след — поэтому режим только по выбору.
- На испытательной таблице (калибровка SD READ, нет Evo) не смешивается. CHECK 18 — выводимый кадр
  смешан; во flash Tang — бит 19 слова 1 ячейки настроек.
- Нагрузка на SDRAM: чтение кадров вдвое. Писатель кадра с 1.32 пишет пачками до 64 слов (как
  читатель): при записи по пакету в 8 слов FIFO захвата на 720p с FRAME BLEND переполнялся.
  Проверка — `sh scripts/run_fb_sim.sh hd 1 1 avg` (16:9, 95 %).
- На плате работает (ядро 1.32, ESP 0.1.99, 2026-10-25).

## Выход HDMI: AVI InfoFrame

`hdmi_tx` (в сборке 720p вместо DVI): преамбула и защитная полоса перед каждой активной строкой
(видео задержано на 10 тактов) и раз в кадр, по фронту VSYNC, островок данных с пакетом
AVI InfoFrame (CEA-861, версия 2): **RGB полного диапазона** (Q = 2), **компьютерный источник**
(ITC = 1) типа **«игра»** (CN = 3), **без обрезки** (S = 2, underscan), формат кадра 16:9,
VIC 19. Заголовок и подпакеты — с кодом BCH (1 + x⁶ + x⁷ + x⁸). В DVI телевизор решает сам:
принимает RGB за видео-диапазон 16–235 («переконтраст»), обрезает края, включает обработку.
Что из флагов выполнит конкретный телевизор — решает он. Старый LG пользователя флаги
ITC/«игра» не выполнил: яркость всего экрана «гуляла» по содержимому кадра — это его
подсветка и контраст по средней яркости, в сигнале Tang её нет (каждая точка выводится
независимо). Помогло в настройках телевизора: энергосбережение — выкл., режим изображения
«Эксперт»/«Кино», динамическая контрастность — выкл. (2026-10-16). Проверка — `tb/tb_hdmi_tx.sv`: поток разбирается по преамбулам, как в приёмнике
(`sh scripts/run_fb_sim.sh` его не запускает: `iverilog … rtl/tmds_encoder.sv rtl/hdmi_tx.sv
tb/tb_hdmi_tx.sv`).

## Оверлеи ESP и меню настроек

С ядра 1.10 экранного меню в ПЛИС нет (`fb_osd` удалён). Вместо него — два **оверлея**
([fb_ovl.sv](../Firmware/rtl/fb_ovl.sv)): прямоугольники с картинкой, которую рисует ESP, поверх
выхода HDMI — и кадра Evo, и кадра FT812. Для меню настроек Tang, обложки в плеере, спектра.
Оверлей 1 лежит поверх оверлея 0.

- **Холст** — в SDRAM Tang, регион 512 КБ (слова 0x108000…0x127FFF): точка RGB565, две в слове
  ([15:0] — левая). Строка холста — ⌈w/16⌉·8 слов (ширина, округлённая до 16 точек), строка r —
  с BASE + r·шаг слов региона. ESP пишет регион окном LINK 0x80000…0xFFFFF подряд, одной
  транзакцией любой длины; запись идёт через очередь 32 слова в домен SDRAM пакетами по 8 слов,
  переполнение очереди — бит OVL_STAT.
- **Настройки** (регистры OVLk_*, ниже): вкл., ×2 (точка холста — 2×2 точки вывода), положение
  на выводе, размер холста (ширина ≤ 1024), начало холста в регионе, прозрачность a = 0…15:
  вывод = картинка + ⌊(оверлей − картинка)·(a + 1)/16⌋, 15 — непрозрачный. Умножение — на блоках
  DSP (MULT9X9), LUT почти не берёт. Настройки защёлкиваются в начале кадра вывода — оверлей
  не рвётся при перемещении.
- **Строки холста** читаются заранее: в конце строки вывода y заказывается строка для y + 2; у
  каждого оверлея два буфера строки по 1024 точки в BSRAM. Не успела — видна прежняя строка.
  Чтение SDRAM — у оверлеев высший приоритет; оба оверлея вместе разумно держать в ~640 точках
  холста на строку при ×1 (×2 читает строку холста раз на две строки вывода).
- Конвейер — 5 тактов точки; синхроимпульсы задержаны так же, развёртка не меняется.

**Меню настроек Tang рисует ESP** ([tang_menu.cpp](../../ESP32%20S3%20Zero%20N8R8/Firmware/src/tang_menu.cpp),
с `vdac4-0.1.75`; меню выводится только так): оверлей 0, холст 336×136 (с `vdac4-0.1.98` —
до 336×144: пункт FRAME BLEND у ядра TS-Config 1.32+; 40 × 15 знакомест
шрифтом 5×7 прежнего меню, рамка 8 точек) ×2 — 672×272 по центру кадра 720p, прозрачность 12,
фон тёмно-синий. С `vdac4-0.1.76` в меню только настройки — пункты прежнего меню; строки
состояния входа (растр, PCLK, окно, картинка, SDRAM) убраны: они в сетевой консоли (`tang`).
ESP раз в 250 мс читает STATUS…CHECK, CTRL и ADJUST и перерисовывает изменившиеся строки.
Меню ПЛИС в ядра не возвращается и при отдельном ядре FT812: оно стоило бы ~1000 LUT в
каждом ядре (решение пользователя 2026-10-18).

**Экран проигрывателя рисует ESP** (`player_overlay.cpp`, с `vdac4-0.1.85` и PLAYER.ELF 1.21;
[Docs/VDAC4.md](../../ESP32%20S3%20Zero%20N8R8/Docs/VDAC4.md), «Экран плеера на HDMI Tang»):
оверлей 1, холст 640×360 ×2 — весь кадр 1280×720, непрозрачный, со слова 15 872 региона до
конца (115 200 слов). Он задевает конец холста меню (слова 0…22 847): появляясь, экран просит
меню скрыться, и при следующем показе меню пишет свой холст заново. Двойного буфера нет — на
второй холст региона не хватает; появление и уход — общей прозрачностью оверлея по ступени
за кадр.

Меню ведёт **только плагин WC**
[VDAC4 Video Settings](../../ESP32%20S3%20Zero%20N8R8/Network/Video%20Settings/README.md)
клавишами Evo: плагин пишет UI_KEY (`TANG_WRITE`), а ESP с ядром 1.10+ разбирает нажатие сама и
в Tang его не передаёт. После включения Evo и Tang меню скрыто (ядро до 1.9 своё меню при старте
показывало — в 1.10+ меню в ПЛИС нет); через 12 с без нажатий скрывается само (с ESP `0.1.76`;
плагин, пока открыт, повторяет «показать» раз в 5 с) — так и после сброса Evo с открытым
плагином меню на экране не остаётся; кнопки Tang (S1, S2) ядро не читает. Значения UI_KEY: 1 — следующий пункт, 2 — предыдущий, 3 — значение +1, 4 — −1,
5 — показать меню, 6 — скрыть; скрытое меню первое нажатие (кроме «скрыть») только показывает.
Настройки ESP пишет в CTRL и ADJUST, во flash Tang их сохраняет `tang_flash`, как раньше.

## Растры Evo и окно захвата

Графические режимы TS-Config (ZX, 16c, 256c, текст; 256/320/360 точек) меняют только
картинку внутри растра — захват их не различает и не должен. Растры разные
(HDL TS-Labs: `current/video/video_sync.v`, `base/video/video_sync_v.v`, `video_vga_sync_h.v`):

| Режим (`raster_detect`) | Строка VGA, отсчётов 28 МГц | Строк | HS | Кадр | На выходе 50,000 Гц | Окно H/V |
|---|---:|---:|---:|---:|---|---|
| 1 TS-Config Pentagon | 896 | 640 | 104 | 48,83 Гц | повтор раз в 0,85 с | 131 / 45 |
| 2 TS-Config `PENT_312` | 896 | 624 | 104 | 50,08 Гц | пропуск раз в ~12,5 с | 131 / 29 |
| 3 Base Conf Pentagon | 896 | 640 | 106 | 48,83 Гц | повтор раз в 0,85 с | 139 / 45 |
| 4 Base Conf 48k | 896 | 624 | 106 | 50,08 Гц | пропуск раз в ~12,5 с | 139 / 45 |
| 5 Base Conf 128k | 912 | 622 | 106 | 49,36 Гц | повтор раз в ~1,6 с | 139 / 45 |
| 0 незнакомый | любой | любое | — | — | — | по центру |

60 Гц (896×524, 59,64 Гц) не поддерживается — решение пользователя: в Base Conf это
вынужденный режим; такой растр захватывается как незнакомый.

**Автоопределение** (`rtl/raster_detect.sv`, домен захвата): полярность HS/VS — активен
более короткий уровень; длина строки, число строк и ширина строчного импульса. TS-Config
и Base Conf на одном растре различаются шириной HS (104 и 106 отсчётов). Растр считается
захваченным после трёх одинаковых кадров. Каждый кадр получает отметку «целый»: в конце кадра
в FIFO уходит служебное слово, и писатель публикует кадр только с этой отметкой — кадр, во
время которого растр сменился, на экран не попадает. Смена растра не прерывает развёртку
576p50: пока растр перезахватывается (~3 кадра, 60 мс), держится последний целый кадр.

**Окно захвата.** Смещения таблицы — расчётные: TS-Config Pentagon — прежние значения
генлок-тракта; остальные — разницей по HDL (`PENT_312` видимая часть на 16 строк VGA раньше;
Base Conf картинка на 8 отсчётов дальше от HS, начало видимой части одно для трёх растров).
К ним прибавляются поправки `h_adj`/`v_adj` от ESP.

**Автоподстройка по картинке** (`rtl/active_bbox.sv` + `raster_detect`). Режим 360×288
занимает всю видимую область — запаса бордюра нет, окно должно стоять точно до точки.
`active_bbox` за каждый кадр находит границы не чёрной картинки в координатах окна. Если
ширина найденной картинки ровно 720 (высота ровно 576), положение повторилось три кадра
подряд и отличается от профиля не больше чем на 16, окно встаёт по картинке. Это срабатывает
в режиме 360×288 и в любом режиме с цветным бордюром; чёрный бордюр ничего не сбивает.
Применяется только там, где видимая область Evo равна окну: TS-Config и Base Conf Pentagon —
по обеим осям, Base Conf 48k — только по горизонтали (видимых строк 560), 128k — нигде
(видимая область 736×558). Границы картинки выведены наружу — ESP сможет показывать их
и управлять подстройкой сам.

## LINK: настройки и состояние для ESP

Ведомый QSPI — [fb_link.sv](../Firmware/rtl/fb_link.sv): команда 8 бит по IO0, адрес 32 бита
по IO0…IO3, для чтения 8 тактов разворота, данные словами по 32 бита старшим байтом вперёд;
0x01 — запись, 0x02 — чтение. Сдвиговые регистры тактируются самим LINK_SCK (FPGA77, GCLKT_1).
Карта регистров — комментарий в [ts_fb_core.sv](../Firmware/rtl/ts_fb_core.sv):

| Адрес | Регистр | |
|---|---|---|
| 0x00 | ID | `56444334` («VDC4») |

Настройки (CTRL, ADJUST) меняются только по LINK: кнопки Tang с ядра 1.10 не читаются. Поправка окна
своя у каждого растра: при смене растра (TS-Config ↔ Base Conf, Pentagon ↔ 48k) действует
поправка нового.

**ESP** ([tang_link.cpp](../../ESP32%20S3%20Zero%20N8R8/Firmware/src/tang_link.cpp),
[link_spi3.cpp](../../ESP32%20S3%20Zero%20N8R8/Firmware/src/link_spi3.cpp), с 0.1.63) — аппаратный
SPI3 без драйвера ESP-IDF: `spi_bus_initialize()` в этой прошивке вешает ESP внутри
`spicommon_bus_initialize_io()` (пробы 0.1.54–0.1.61 на столе); тактирование, сброс и выводы
через матрицу GPIO делаются своим кодом, транзакции ведёт `spi_hal_*` опросом.
При запуске Tang ищется на 1 МГц, затем выбирается самая высокая частота из 40 / 26,7 / 20 / 13,3 /
10 / 5 МГц, на которой 1000 проверок (запись и чтение SCRATCH, чтение 16 слов со сверкой ID,
версии и SCRATCH) проходят без ошибок; при запаздывании ответа ESP добавляет 1–2 такта разворота.

Проверено на столе (Tang от USB, плата без Evo, 0.1.63): **40 МГц, 8 тактов разворота, 0 ошибок
из 2000**; 1000 чтений по 64 байта — 21 мс (~3 МБ/с вместе с накладными расходами на транзакцию).

LINK запускается, когда запитана плата (линия CS: R10 к шине логики) или сама Tang (LINK_IRQ_N:
подтяжка 10 кОм на модуле Tang). Питание платы ESP определяет по напряжению CS через АЦП:
у Tang, запитанной от USB, линию приподнимает её светодиод на FPGA18 (на столе 1,5 В с подтяжкой
ESP вниз против ~2,7 В от R10), и логический уровень там обманчив — до 0.1.63 ESP в таком
состоянии запускала I2S в обесточенный ЦАП.

Сетевая консоль ESP (порт 23, `tools/net_console.py`): `tang` — сводка STATUS…CHECK и
расшифровка CTRL/ADJUST, `tang rd АДРЕС`, `tang wr АДРЕС ЗНАЧЕНИЕ` (hex). Изменения состояния
и настроек Tang ESP пишет в журнал наладки раз в 2 с.

## Настройки во flash Tang

Flash Tang Nano 20K — XTX XT25F64B (JEDEC `0B4017`, 8 МБ) на выводах MSPI ПЛИС (MCLK 59, MCS_N 60,
MO 61, MI 62; после загрузки ПЛИС — обычные выводы, `use_mspi_as_gpio`). Модуль
[fb_flash.sv](../Firmware/rtl/fb_flash.sv), SCK 18,6 МГц:

| Адрес flash | Что |
|---|---|
| 0x000000…0x0DD89A | прошивка Tang: упакованный `.fs`, ровно то, что пишет Gowin Programmer (сверено побайтно) |
| 0x7FF000, 4 КБ | настройки: 128 ячеек по 32 байта; MAGIC «VDST», MUX CLOCK/DELAY/PHASE, AUTO ALIGN, H/V ADJUST восьми растров, слово 6 — FT SIZE ядра FT812 (ESP 0.1.104), сумма |

- **Загрузка — самим ядром**: через ~1 мс после сброса оно читает сектор до первой чистой
  ячейки и берёт последнюю целую (недописанная при пропадании питания не проходит по сумме).
  Источник и SD READ не хранятся: источник после включения всегда AUTO, SD READ калибруется.
- **Запись — через ESP** ([tang_flash.cpp](../../ESP32%20S3%20Zero%20N8R8/Firmware/src/tang_flash.cpp),
  с 0.1.64): раз в 2 с ESP читает CTRL и ADJ_TAB; изменение, державшееся с прошлого опроса,
  уходит в следующую ячейку (с чтением обратно); когда ячейки кончились — сектор стирается.
  Пишет только при живом ядре: ID и версия сверяются до и после чтения настроек — пока Tang
  грузится (~3 с), LINK читает мусор с подтяжек. Перед каждой командой flash буфер моста
  читается обратно.
- Проверено на столе (0.1.65–0.1.67): настройки, изменённые по LINK, записаны в ячейку 0,
  после перезагрузки Tang (Reprogram) ядро загрузило их само; рабочие значения
  (PHASE 1, DELAY 1, CLOCK B, поправки 0) записаны в ячейку 1.

## Обновление прошивки Tang через ESP

`python tools/tang_tool.py update <IP ESP> fpga/vdac2/impl/pnr/ts_fb_hdmi_top.fs` (в репозитории
VDAC4; порт 8268 ESP, с 0.1.65). ESP принимает образ целиком в PSRAM и проверяет SHA-256,
слово синхронизации A5C3 и IDCODE GW2AR-18 `0000081B` в заголовке и что образ кончается до
блока с настройками (0x7F0000); затем стирает блоки 64 КБ, пишет и читает обратно для сверки.
Новое ядро Tang загружает при следующем включении питания (Evo выключить и включить; на столе —
Reprogram в Gowin Programmer). Проверено на столе: 907 418 байт за 8 с, сверка совпала, Tang
загрузилась с записанного. Каждое следующее ядро обязано сохранить мост к flash (регистры
0x48/0x4C/0x80) — иначе обновлять Tang придётся снова по USB.

## Multiboot: второе ядро в flash Tang (ядра 1.11–1.13)

Для ядра FT812 отдельной конфигурацией ([ft812-emulation.md](ft812-emulation.md), шаг 7). По
UG290 7.5.4 ([документация](references/gowin-multiboot-20261018/README.md)): при включении
ПЛИС всегда грузит битстрим с адреса 0; в заголовке каждого битстрима — адрес перехода, и
импульс RECONFIG_N грузит битстрим оттуда, без выключения питания и сколько угодно раз.

- **Слоты flash Tang по 1 МБ:** слот 0 (0x000000) — ядро при включении (TS-Config), слот 1
  (0x100000) — ядро FT812, настройки — по-прежнему 0x7FF000. Образ — 907 418 байт.
- **Адрес перехода** — опция сборки: `scripts/gowin_fb.tcl` пишет в слот 0 переход в слот 1,
  `scripts/gowin_fb_slot1.tcl` — образ слота 1 с переходом обратно в 0 (заголовок
  `D2 00 FF FF 00 10 00 00` / `… 00 00 00 00`; у ядер до 1.11 там 0 — BOOT перезагрузил бы
  их в себя же). Слот 1 пока — то же ядро с BOOT, читающим «слот 1»: проверочный образ.
- **Перезагружает BL616 по JTAG (ядро 1.13, прошивка BL616 4).** На Tang Nano 20K вывод
  RECONFIG_N (FPGA9) идёт только на контрольную точку TP1 (схема rev 1.30). Ядра 1.11–1.12 тянули
  его сами (`use_reconfign_as_gpio`, открытый сток), но на столе 18.10.2026 ПЛИС от этого не
  перезагрузилась: запись «BOOT» дошла, ядро работало дальше, метка ESP в SCRATCH цела; по
  UG290 перезагрузку запускает импульс на выводе с функцией RECONFIG_N, а в режиме GPIO это
  обычный вывод. Поэтому с 1.13 ядро только просит: `boot_req` (запись «BOOT», автопереход по
  обмену с FT812, возврат после тишины) — бит 7 флагов STATUS связи с BL616 и IRQ_N
  (`cp_link.sv`); BL616 за ≤ 10 мс видит его и даёт JTAG Reconfig (IR 0x3C, затем NOOP 0x02,
  `bl616/app/fpga_jtag.c`) с выводов GPIO10/12/14/16 — тех же, что у USB-JTAG FPGA Partner
  (настройку выводов он сохраняет и возвращает). Reconfig по JTAG грузит битстрим по адресу
  перехода multiboot (проверено на столе: Reprogram программатора уходил в слот 1). ESP
  ничего не меняет: `tang boot` и `ft_open` по-прежнему пишут «BOOT». Бит 19 регистра BOOT —
  «перезагрузка запрошена».
- **Время загрузки** — частота MCLK из заголовка: при 2,5 МГц (по умолчанию) ~2,9 с, 25 МГц —
  290 мс, 41,667 МГц — 174 мс, 62,5 МГц — 116 мс (предел GW2AR-18 — 66,6 МГц). Скрипт
  принимает `set loading_rate 41.667` перед `source`. С 1.18 ядро FT812 слота 1 —
  41,667 МГц (`gowin_fb_slot1.tcl`, ~0,2 с): программы Evo, которые ждут FT812 недолго
  (просмотрщик текста WC — «VDAC2 не найден»), загрузку ~2,9 с не дожидались; на плате так и
  работает. С 1.22 и слот 0 — 41,667 МГц (`gowin_fb.tcl` по умолчанию), а ядро FT812 уходит в
  слот 0 после 0,5 с тишины (`SWITCH_IDLE_MS`, было 3 с): возврат из ядра FT812 — ~0,7 с вместо
  ~6 с. Программа, которая снимает M_SEL дольше 0,5 с и снова идёт к FT812, получает ядро
  заново (RAM_G пуст).
- **ESP** (0.1.76): `tang_tool.py update --slot 1 <IP> ts_fb_slot1.fs` пишет образ в слот
  (`BEGIN <размер> <sha256> <адрес>`); `tang boot` в сетевой консоли проверяет во flash
  заголовок слота перехода (A5C3, IDCODE) и пишет «BOOT». Перезагрузку ESP видит по
  SCRATCH (ESP держит там метку, после загрузки ПЛИС он 0): заново читает версию, настройки
  flash и загружает меню в новое ядро.

**Ядра 1.12 — два состава одного RTL** (`ts_fb_core`, параметры HAS_EVO / HAS_FT; скрипты —
переменная `core_kind`: `both`, `evo`, `ft`), образы — [out/core_1.12](../Firmware/out/core_1.12/README.md):

| Ядро | Слот | Что внутри | Логика | CLS | BSRAM |
|---|---|---|---:|---:|---:|
| TS-Config (`evo`) | 0 | захват Evo, кадровый буфер, оверлеи, LINK, flash, связь с BL616 (почтовый ящик — для её обновлений) | 6 601 (32 %) | 49 % | 14/46 |
| FT812 (`ft`) | 1 | эмулятор FT812, растеризатор, кадр FT через 720p, оверлеи, LINK, flash, BL616 | 17 167 (83 %) | 93 % | 39/46 |
| общее (`both`) | — | всё, как в 1.10/1.11 | 18 652 (90 %) | 97 % | 40/46 |

- **TS-Config → FT812:** посылка Evo, которая запускает чип: ACTIVE (`00 00 00`) или обращение к
  памяти FT812 (адрес, старшие биты `00`/`10`; ≥ 16 тактов SCK за один выбор FT_CS_N, а не
  помеха на линии), — если ESP разрешила: «ARM1» в BOOT. С 1.16 команды хоста без ACTIVE
  (CORERST, PWRDOWN, SLEEP, CLKEXT, CLKSEL) перехода не включают: ими FT812 гасят при сбросе
  Evo, и до 1.16 Tang уходил в ядро FT812 и обратно при каждом сбросе. Что Evo шлёт FT812 —
  FT_SEEN (0x50) и FT_COUNT (чтение 0x54). ESP 0.1.76 разрешает его при запуске
  LINK и после каждой перезагрузки Tang, только если в слоте 1 битстрим, а на время записи
  слота — запрещает. В ядре TS-Config MISO FT812 — 0: программа, ждущая `REG_ID = 0x7C`,
  ждёт, пока грузится ядро FT812.
- **FT812 → TS-Config:** M_SEL = 0 и 3 с без обмена с FT812 (отсчёт — от последнего обмена).
  Пока M_SEL = 0, ядро FT812 выводит чёрное поле: картинки TS-Config в нём нет.
- **Ядро FT812** показывает кадр FT всегда (кроме испытательной таблицы: калибровка SD READ
  и SOURCE = TEST); захвата Evo, PLL захвата и `raster_detect` в нём нет, VERSION — личность 02.
  Меню ESP в нём — без пунктов мультиплексора и окна.
- **Хост FT812 — ESP** (FT_CFG бит 2, `tang fthost on`): SPI Evo к FT812 отключён — FT_CS_N и
  такты Evo до `ft_spi`/`ft_core` не доходят, MISO к Evo — 0, INT_N для Evo неактивен
  (прерывание видно ESP в FT_STAT); ESP ведёт FT812 окном FT_ADDR/FT_DATA. Возврат в
  TS-Config — только по M_SEL = 0 (3 с): обмены Evo в этом режиме не в счёт.
- Проверено в симуляции (`run_fb_sim.sh`): оба состава, автопереход по ACTIVE и по чтению
  REG_ID после «ARM1», не без него и не по командам хоста без ACTIVE, автовозврат после тишины
  и не во время обмена; оверлеи — холст меню 336×136 окном LINK слово в слово
  (`tb/tb_fb_ovl.sv`: до 1.16 терялось первое слово каждого пакета — меню шло полосами).

Образы ядра 1.11 — [fpga/vdac2/out/core_1.11](../Firmware/out/core_1.11/README.md): слот 0 с частотой
загрузки по умолчанию и с 41,667 МГц, слот 1 с 41,667 МГц; логика 90 %, CLS 97 %, тайминг
сходится во всех трёх (слот 1 разводится с размещением 0).

**USB-JTAG (Gowin `programmer_cli` 1.9.11.03) — только слот 0.** На столе 18.10.2026 запись с
`--spiaddr 0x100000` не прошла сверку, а следующая такая же испортила слот 0 (при включении —
ошибка CRC, регистр состояния `0x4421`). Слот 1 пишет только ESP (`tang_tool.py update --slot 1`,
со сверкой чтением). JTAG Reprogram (`--run 1`) у образа с multiboot уходит по адресу перехода
в слот 1, как RECONFIG_N, — слот 0 проверяется включением питания (`--run 74`: бит 13 — Done).

Проверка на столе, так, чтобы любой сбой лечило выключение питания (без USB). Итог 18.10.2026:
шаги 1–2 пройдены (ядро 1.11, слот 1 записан ESP со сверкой), шаг 3 — нет: `tang boot` ПЛИС

## Обновление прошивки BL616 через ESP

`python tools/tang_tool.py bl616 <IP ESP> bl616/app/out/vdac4_copro_bl616.bin` (ESP 0.1.74+,
ядро Tang 1.8+, прошивка BL616 2+; первую с обновлением по сети ставят по USB —
`bl616/README.md`). ESP принимает образ (заголовок BFNP, до 256 КБ), проверяет SHA-256 и
кусками по 1984 байта кладёт его в почтовый ящик ядра Tang (окно MBOX, MB_PAGE), ожидая на
каждый кусок ответа BL616 в CP_INFO. BL616 собирает образ в RAM, проверяет SHA-256 и
заголовок, пишет во flash с 0x40000 (FPGA Partner с 0x0 не трогается), сверяет и
перезагружается; OK приходит, когда новая прошивка уже пишет обычное CP_INFO. Протокол —
`bl616/app/fw_mailbox.h`; обе стороны вместе проверяет `bl616/app/test/run_update.sh`.

Порт 8268, как и консоль 23, открыт в локальной сети без пароля.

## Чем проверено

Масштаб (тестбенч `tb_ts_fb`, ASPECT = 0 и 1, `sh scripts/run_fb_sim.sh hd [1]`): каждая точка
выхода сверяется с точкой источника по точной формуле ⌊x·720/W⌋, ⌊y·576/720⌋; поля вокруг
картинки — чёрные. Режим точка в точку (уменьшенные растры, сборка HD = 0) — прежние сценарии.

Оверлеи (`OVL_TEST`, в сценариях с испытательной таблицей): тестбенч пишет оба холста окном LINK
0x80000…, затем регистры: оверлей 0 — 32×12 в (8, 4), ×1, непрозрачный; оверлей 1 — 16×8 в
(24, 10), ×2, прозрачность 7, частично поверх оверлея 0. С кадра, где настройки взяты, каждая
точка выхода в прямоугольниках сверяется со смешением по формуле (точка холста — узор от
координат), вне их — с таблицей.

Тестбенч [tb_ts_fb.sv](../Firmware/tb/tb_ts_fb.sv): модель растра Evo (любой из таблицы,
смена на лету, любая полярность, сдвиг картинки) → мультиплексор с задержкой 4,5 нс → тракт →
**модель SDRAM с проверкой протокола** ([sdram_model.sv](../Firmware/tb/sdram_model.sv):
tRCD, tRP, tRC, tRAS, tWR, tRFC, регенерация, открытая строка, конфликт шины) →
**декодер TMDS**: выход проверяется так, как его увидит монитор. Номер входного кадра
закодирован в строке 0, а картинка от него зависит — склейка двух кадров ловится сразу.
Три тактовых генератора независимы, как на плате. Icarus Verilog 13.0.

Настоящие размеры, картинка — экран ZX «Hibernated 1» в синем бордюре
(`scripts/scr2hex.py`), сверка выходного кадра со входом до точки (`scripts/fb_compare.py`):

| Сценарий | Итог |
|---|---|
| TS-Config Pentagon 896×640 → 576p50 | режим 1, 3 кадра с картинкой, **0 расхождений**, 0 нарушений SDRAM |
| Base Conf 48k 896×624 → 576p50 | режим 4, 4 кадра, **0 расхождений** |
| Смена растра Pentagon → 48k на лету | перезахват за 60 мс, 2 кадра на стыке отброшены, кадры нового растра — 0 расхождений |
| 360×288 без бордюра, картинка сдвинута на +3/−2 | окно подстроено 131/45 → 134/43 за 3 кадра после захвата растра; все 4 кадра после подстройки — **0 расхождений**, рамка в одну точку по краю на месте |

Уменьшенные растры (много кадров за минуту):

| Сценарий | Итог |
|---|---|
| Вход медленнее выхода на 17 % | повторы по расчёту, пропусков нет |
| Вход быстрее на 6 % и на 11 %, незнакомый растр | окно по центру, пропуски по расчёту |
| Положительные HS/VS | полярность определена верно |
| Смена растра A → B и B → A | перезахват ~5 кадров, сбойные кадры не показаны |
| PCLK пропадает посреди кадра | развёртка идёт, держится последний кадр |
| Картинка сдвинута на +3/−2 и −5/+1 | окно встало по картинке, дальше все кадры точны |

Проверки развёртки в каждом кадре: полная строка, ширина строчного и кадрового импульсов,
число строк, число активных строк и пикселей, период кадра (20,0005 мс — отличие от 20,0000
из-за округления периода 27 МГц в тестбенче). Запуск: `sh scripts/run_fb_sim.sh [full]`.

По ходу первой настоящей сборки найдены и исправлены ошибки, которые прятались, пока
проект проверялся только симуляцией и Yosys (касаются и генлок-прошивки):

- `IO_TYPE=LVDS25` на выводах HDMI недопустим для эмулированного LVDS — нужен `LVCMOS33D`;
- в `async_fifo` признак «полон» образовывал комбинационную петлю — стал регистром;
- Gowin не принимает перенос строки через `\` в SDC;
- объявление `wire a, b, gnd = 1'b0;` Gowin отвергает — разнесено;
- макрос `SYNTHESIS` в Gowin задать нечем, поэтому смысл перевёрнут: заглушки для симуляции
  включаются макросом `SIMULATION` (`-DSIMULATION`), синтез по умолчанию берёт примитивы.

## Что проверить на железе

- Фазу клока SDRAM (сейчас — инверсия клока логики) и `RD_LAT` в `sdram_burst`.
- Примет ли монитор 576p50 по HDMI/DVI (часть ПК-мониторов 576p не принимает).
- Всё, что перечислено для генлока: `SAMPLE_DELAY`, `SEL_PHASE`.
- Смещения окна для каждого растра — программой 360×288 с рамкой по краю или с цветным
  бордюром (автоподстройка покажет разницу с таблицей; её стоит перенести в таблицу).
- Ширину HS у TS-Config и Base Conf (104/106) — от неё зависит различение конфигураций.
- Регенерация SDRAM сделана по 7,8 мкс (8192/64 мс) — вдвое чаще, чем нужно микросхеме
  на 4096 строк; запас оставлен сознательно.
